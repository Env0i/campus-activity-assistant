# 1.3.4 发版记录（2026-11-28）

这一版修复「安装在默认位置时增量更新包因路径超长应用失败、被迫改下完整更新包」。记录验收数字与发版口径，供后续发版与审计回查。

## 这一版没附带增量包

发版命令用 `--prepare --no-delta`，所以**旧客户端那次演练不用跑**（规格要求的「上一个已发布版本的客户端代码 + 本次增量包」演练只对随版增量生效）。

不附带的原因（2026-11-28 演练实测）：

- 旧客户端（1.3.3 及更早）应用增量前，先把整份旧版本目录复制进三层叠拼的暂存工作目录（`.staging-<请求号>` 叠 `.stage-` 叠 `.part-`，共 109 字符）。正式 1.3.3 里仍带着路径最长的调试资源（`lib/vite` 下 97 字符相对路径文件），于是 61 + 用户名长度 + 1 + 109 + 1 + 97 在任何用户名下都超过 259。
- 演练一实测：用户名 7 字符最长路径 276、用户名 8 字符最长 277，均不通过。1.3.3 升 1.3.4 的过渡增量在没开长路径支持的机器上一律失败回退完整包——附带它只会让用户白下约 59 MiB 再改下 72 MiB 完整包。
- 1.3.2 的基线增量约 60 MiB，与完整包体量相当，同样不值得附带。

## 修复后的验收数字

- 构建核对：版本目录里 `lib/vite` 与 `lib/tools/skills` 不存在，`_internal/w/grab-worker.exe` 存在，最长相对路径 **80**（`_internal/setuptools/_vendor/importlib_metadata-8.7.1.dist-info/licenses/LICENSE`）。
- 演练二（修复后客户端自己的更新代码，等长版本根、用户名 20 字符）：**通过**，实测最长路径 **182**，工作目录为独立短名（前缀 + 12 位十六进制）。上限 259。
- 两种形态 `--runtime-check --report` 均退出 0 且 `ok: true`（独立 EXE 在只放它的空目录、版本目录主程序，内置 worker 正常启动）。
- 离线回归：本机版全量与发版测试全量均不比基线多失败；代码结构检查通过。

## 什么条件下会再坏

- 从下一版起恢复附带增量前，必须先按规格对「上一已发布版本客户端 + 本次增量包」与「当前代码 + 本次构建两次之间的增量」各跑一次 `tools/release/rehearse_upgrade.py`（用户名长度 20）：前者允许按预算失败但要把判定与最长路径写进发版记录，后者必须通过。
- 旧客户端（1.3.3 及更早）到本版的升级只有完整包一条路，属于已知且预期的行为；它们在程序内检查更新会正常走「下载完整更新包」。
