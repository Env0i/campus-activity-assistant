# 手机访问与手机页真实验收清单（2026-10-31）

本文件收集此前自动化通过、但没有在真实手机、真实桌面程序或真实学校业务条件下完成的验收项目。
自动化测试、源码检查和本地夹具结果只能说明代码路径可运行；只有按本清单操作并记录结果，才算用户验收。

当前学校没有可报名活动时，D 组必须记录为“暂缓：当前没有真实活动”，不能用虚构活动或测试数据写成通过。

## 一、填写规则

每完成一项，在表格中记录：

| 字段 | 写法 |
|---|---|
| 日期时间 | 使用本地时间，精确到分钟即可 |
| 设备 | 手机型号、系统和浏览器；可写简称 |
| 通道 | `Tailscale` 或 `Cloudflare` |
| 结果 | `通过`、`失败`、`暂缓`、`无法观察` |
| 现象 | 只写界面可观察结果、是否能继续操作、是否需要重新配对 |
| 证据 | 截图或日志编号；二维码、地址、配对码、cookie、账号、密码、验证码必须打码或不保存 |

遇到“提交后没有立即结果”的情况，不要再次点击提交。先等待状态对账，或按该项的“未知结果”步骤恢复。这样可以避免把一次请求变成重复报名。

## 二、验收顺序与准备

建议先做 A 组和 B 组，再做 C、E、F、G，最后等待真实活动后做 D 组。每组开始前：

1. 电脑程序保持打开，确认手机访问通道显示为可用。
2. 手机只保留一个本项目页面标签；另一个浏览器或无痕窗口只在明确要求时使用。
3. 先用 Tailscale 做长期通道验收，再用 Cloudflare 做临时通道验收。
4. 记录开始时的连接状态和“最近同步”时间，便于判断是否真的发生了刷新。
5. 不要在没有明确选定活动的情况下点击报名开始；学校没有活动时直接跳过 D 组。

第一批建议现在执行：**A1、A2、A3、A4、B1、B2、B3、B4**。A 组主要看自适应同步和后台恢复，B 组主要看两个通道的配对与生命周期。

## 三、A 组：手机页自适应同步与网络恢复

### A1：前台空闲同步不是每秒刷新

**前置条件**

- 手机已经配对并进入主界面。
- 没有报名计划正在运行，也没有进行中的重登。
- 手机页面保持前台可见。

**步骤**

1. 记下页面首次显示的“最近同步”时间。
2. 保持页面不操作至少 60 秒，期间不要点刷新、开始、停止或重登。
3. 观察“最近同步”是否大约每 15 秒变化一次；至少记录三次变化的时间。
4. 同时观察页面是否稳定显示“已连接”，按钮是否没有无故变灰。
5. 连续快速点两次“刷新”，只记录第一次点击后的按钮状态和最终结果。

**通过判据**

- 空闲时不是每秒刷新；相邻同步大致接近 15 秒。
- 快速连点只出现一个“刷新中…”过程，恢复后按钮可再次点击。
- 页面没有因为等待而出现“状态已过时，先刷新再开始/重登”。

**记录**

- 三次同步时间间隔：`__ 秒 / __ 秒 / __ 秒`。
- 连点表现：`单次请求 / 看不出 / 疑似重复`。

### A2：进行中状态使用较快同步

报名活动暂缺时，可用“手机续登录”作为进行中状态；如果重登在电脑上瞬间完成，记录“无法观察活动态”，不要把它写成失败。

**步骤**

1. 在手机页打开“电脑续登录”区域，点击“在手机上重登”。
2. 从点击开始，连续观察约 10 秒，不要重复点击。
3. 如果出现验证码输入区，保持在等待输入状态；如果电脑有 ddddocr 且显示“电脑正在自动重登”，观察手机是否隐藏验证码区。
4. 观察“最近同步”、重登状态和按钮是否大约每 2 秒更新一次。
5. 成功、失败或取消后，确认页面回到稳定状态，按钮没有永久禁用。

**通过判据**

- 重登进行中比空闲状态更新更及时，界面不会长时间停在旧状态。
- 自动重登时不要求手机输入不存在的验证码。
- 重登结束后控件收口，页面可以再次刷新或发起下一次操作。

**无法观察的情况**

- ddddocr 识别和提交过快，无法看到 2 秒活动态：记录“自动流程过快，最终状态为 __，未观察到中间态”。
- 既没有真实登录过期，也无法安全触发重登：记录“暂缓”，不要修改账号状态来制造场景。

### A3：锁屏或切后台后停止定时器，回前台立即补一次

**步骤**

1. 在手机主界面保持已连接，记下当前“最近同步”时间。
2. 锁屏至少 60 秒；如果系统不允许观察锁屏，改为切换到另一个应用至少 2 分钟。
3. 回到本项目页面，观察页面是否立即更新一次。
4. 回到前台后的 30 秒内不要操作，观察是否出现连续快速刷新或“状态已过时”。
5. 再手动点一次刷新，确认按钮仍可用。

**通过判据**

- 页面后台期间没有因系统定时器行为出现大量请求或错误提示。
- 回到前台后能补一次状态，按钮立即可操作。
- 没有因为后台停留而错误显示过时；若网络确实断开，必须显示可读的离线原因。

### A4：Wi-Fi / 蜂窝切换后的离线与恢复

**步骤**

1. 手机通过 Wi-Fi 打开主界面，确认“已连接”。
2. 临时关闭 Wi-Fi，切换到蜂窝数据；如果现场没有蜂窝数据，关闭网络 10–20 秒后再恢复。
3. 在断网期间观察连接状态、离线提示、刷新按钮和重试次数。
4. 网络恢复后点一次“刷新”，等待完整结果，不要连点。
5. 如果切换后地址发生变化，先确认仍能访问同一个通道地址，再判断功能。

**通过判据**

- 断网后页面显示“连不上电脑”或等价的可读提示，刷新按钮不会永久卡住。
- 网络恢复后能回到“已连接”，失败计数清零。
- 断网期间误点的写操作不会显示为成功；恢复后不会自动重复提交。

### A5：需要重新配对时停止轮询

**步骤**

1. 在电脑端点“关闭手机访问”，或使用本清单 B6 让设备信任撤销。
2. 手机页面点击“刷新”。
3. 观察是否回到配对页；停留 60 秒，不输入配对码。
4. 观察是否仍然持续显示请求中的刷新或不断弹出错误。
5. 电脑重新开启 Tailscale 通道后，扫码并输入新配对码，确认同步恢复。

**通过判据**

- 失去配对后回到配对页，并停止后台轮询。
- 重新配对后恢复主界面和正常同步。

## 四、B 组：Tailscale 与 Cloudflare 通道生命周期

### B1：Tailscale 首次扫码配对

**步骤**

1. 电脑端选择 Tailscale，确认帮助页显示地址、二维码和配对码。
2. 手机用相机扫描二维码打开页面；不要先手动改地址。
3. 在配对页确认页面说明用途，输入电脑当前显示的配对码，点击配对。
4. 进入主界面后，确认连接状态、今天/即将开放区域和“加进手机书签”提示。
5. 复制地址到浏览器地址栏重新打开一次，记录是否仍能进入已配对主界面。

**通过判据**

- 扫码能打开正确页面，配对码正确后进入主界面。
- 页面没有把账号、密码、验证码或配对码写进可见日志。
- 同一地址在当前浏览器上下文重新打开时，设备信任生效。

### B2：Tailscale 重启后免重新扫码

**步骤**

1. 先完成 B1，确认手机已经进入主界面。
2. 在电脑端正常退出程序；不要点击“关闭手机访问”后再退出，因为那是主动撤销设备信任的另一条路径。
3. 重新启动程序，等待 Tailscale 通道自动恢复并显示可用。
4. 手机打开原来的地址或书签，点击一次刷新。
5. 观察是否直接恢复主界面，是否仍显示“已连接”。
6. 点一个低风险读操作（刷新或展开已报名摘要），确认新会话可用。

**通过判据**

- Tailscale 地址保持可用，手机不要求重新扫码或输入配对码。
- 读操作正常；如需验证写操作，使用 B2 后的“显示电脑窗口”或 C5，确认新 CSRF 也能工作。

### B3：Cloudflare 首次开启与重新配对

**步骤**

1. 电脑端停止当前手机访问；确认旧通道已经收口。
2. 选择 Cloudflare，点击开启，等待临时地址出现。
3. 手机扫描新二维码，输入新配对码，进入主界面。
4. 记录“地址指纹”即可，例如只记域名首尾各一小段；不要把完整临时域名写入文档。
5. 正常退出程序并重新启动。
6. 观察 Cloudflare 是否不会自动恢复；如果需要手动重新开启，开启后记录新地址指纹。
7. 用手机打开新地址，重新扫码并输入配对码。

**通过判据**

- Cloudflare 可用于临时访问，当前隧道存活期间不需要反复配对。
- 程序重启后需要手动开启，通常会得到新地址；新地址需要重新配对。
- 旧地址失效后，页面不会继续展示旧二维码或旧地址。

### B4：Cloudflare 异常退出后的收口

**步骤**

1. 按 B3 开启 Cloudflare，并让手机保持主界面。
2. 在电脑任务管理器中结束本项目使用的 cloudflared 进程；只结束该进程，不结束整个程序。
3. 回到电脑帮助页或手机页，执行一次刷新。
4. 观察旧地址、二维码、通道状态和手机访问是否同时收口。
5. 手机再刷新一次，确认不会继续拿旧页面执行写操作。
6. 电脑重新开启 Cloudflare，比较新旧地址指纹；手机重新扫码和配对。

**通过判据**

- 第一次发现异常后，旧地址和旧二维码消失，状态明确显示隧道已退出或不可用。
- 重新开启得到新地址，旧配对不能直接复用。
- 退出提示不会在下一次普通状态读取中降级成“可用”。

### B5：二维码、手动地址和手机书签三条入口

**步骤**

1. 用二维码完成一次配对，按页面提示把地址加入手机书签。
2. 关闭当前标签页，从书签重新打开；观察是否进入主界面或要求重新配对，并记录浏览器类型。
3. 新开一个普通标签页，手动输入同一地址，观察与书签打开的行为是否一致。
4. 对 Cloudflare 重开后的新地址重复一次，只验证入口与提示，不保存完整地址。

**通过判据**

- 三处“建议加入手机书签”的提示位置清楚，点击后用户知道下一步怎么做。
- 书签重新打开时，行为符合通道规则：Tailscale 长期地址可恢复；Cloudflare 新隧道需要新配对。
- 若二维码打开和手动输入落在不同浏览器存储上下文，记录为浏览器行为差异，不把它误判为服务器故障。

### B6：主动关闭手机访问后的撤销

**步骤**

1. 在 Tailscale 通道已配对的情况下，电脑端点击“关闭手机访问”。
2. 手机刷新原页面，确认回到配对页或显示通道已关闭。
3. 等待 60 秒，确认不会自动恢复主界面。
4. 电脑重新开启 Tailscale，手机扫码并输入新配对码。

**通过判据**

- 主动关闭会撤销旧会话和设备信任，手机不能继续写操作。
- 重新开启后必须重新配对；新配对后恢复正常。

## 五、C 组：手机续登录、验证码和结果对账

### C1：电脑自动重登路径（已安装 ddddocr）

**前置条件**

- 电脑端 ddddocr 已安装并显示可用。
- 账号密码已经通过产品入口保存；不在文档记录任何凭据。
- 有一个可安全触发的登录过期场景。

**步骤**

1. 手机打开“电脑续登录”卡，先记录整体状态、OCR 状态、凭据状态和最近方式。
2. 触发续登录，观察手机是否显示“电脑正在自动重登”或等价文案。
3. 在自动处理期间，确认验证码图片、验证码输入框和手机提交按钮整体隐藏。
4. 等待最终状态；自动流程过快时只记录最终结果和“未观察到中间态”。
5. 登录成功后，刷新手机页，确认“登录已过期”提示消失，活动状态重新可读。

**通过判据**

- ddddocr 可用且自动处理未达到人工阈值时，手机不展示过期验证码图。
- 自动成功后，页面回到可操作状态，不停留在“登录已过期”。

### C2：手机人工续登录路径

**前置条件**

- 电脑未安装 ddddocr，或自动重登已达到转人工阈值。
- 具备可用的账号密码；不把它们写入证据。

**步骤**

1. 点击“在手机上重登”。
2. 等待验证码区出现，确认图、输入框和提交/换图/取消按钮一起出现。
3. 输入验证码，点击提交一次；提交期间不要重复点击。
4. 观察状态从等待、校验到成功或失败的变化。
5. 成功后刷新，确认活动状态恢复；失败后确认页面保留可读原因和下一步操作。

**通过判据**

- 验证码区整体显示或整体隐藏，没有只剩一个孤立输入框的情况。
- 提交中按钮保持禁用或显示处理中，结果明确后才恢复。
- 成功后电脑和手机状态一致。

### C3：真实验证码错误与密码错误提示

这项只验证界面是否正确呈现已经取得的真实学校接口结果；不要在文档中写入账号、密码、验证码或 token。

**场景一：验证码错误**

1. 使用正确账号密码，输入一个故意错误的验证码。
2. 提交一次，等待结果。
3. 记录页面是否显示“登录失败，验证码不正确！”或同义的真实文案。
4. 确认验证码刷新为新图；没有倒计时要求，用户可以在刷新后继续输入。

**场景二：密码错误**

1. 使用正确账号、故意错误的密码和正确验证码。
2. 提交一次，等待结果。
3. 记录页面是否显示“账号或密码错误！”或同义的真实文案。
4. 确认失败后验证码可以重新获取。

**通过判据**

- 两类错误在页面上能区分，不能都显示成“重登失败”。
- 失败后不会自动重复提交，也没有验证码倒计时误导。

### C4：重复点击保护

**步骤**

1. 在人工重登提交按钮可用时，快速点击两次。
2. 观察按钮是否立即进入处理中并禁用。
3. 等待最终结果，检查手机日志或页面状态只出现一次提交结果（日志只记录请求类型，不记录敏感值）。

**通过判据**

- 同一张验证码只产生一次提交。
- 第二次点击不会新建第二场重登，也不会把第一场状态清掉。

### C5：提交结果未知后的对账与恢复

**步骤**

1. 进入人工验证码提交状态，点击提交一次。
2. 在提交后立即切断手机网络，或切换网络使本次响应暂时不可达。
3. 观察手机是否显示“校验中/提交待确认/结果未知”一类状态；不要再次提交。
4. 恢复网络，等待自动对账；必要时点一次刷新。
5. 根据最终状态确认成功、失败或可安全重试。

**通过判据**

- 结果未知期间验证码区和提交按钮保持正确禁用，不会误显示已失败并鼓励重复提交。
- 恢复网络后能按服务端最终结果收口。
- 如果服务端已成功，页面不会再发第二次提交。

### C6：电脑重启后的写操作与 CSRF 更新

**步骤**

1. 在 Tailscale 已配对的手机页面保持主界面。
2. 正常退出并重新启动电脑程序，等待手机访问自动恢复。
3. 手机刷新一次，确认读状态正常。
4. 点击“显示电脑窗口”或其他低风险写操作，观察是否成功。
5. 如需验证续登录，再执行 C1 或 C2；不要直接重复报名。

**通过判据**

- 读操作和写操作都使用新会话正常工作，不出现持续 `bad_csrf`。
- “显示电脑窗口”成功时，电脑窗口恢复可见。

## 六、D 组：真实活动报名、停止、取消

本组必须使用用户明确指定的真实活动。当前没有可报名活动时，四项都记录“暂缓：无真实活动”，不补造通过结论。

### D1：查看活动与已报名摘要

1. 手机刷新，确认活动名称、报名时间和状态与电脑端一致。
2. 展开“已报名”摘要，核对数量和已报名项目。
3. 记录没有活动时是否显示清晰的空状态，而不是报错或旧数据。

### D2：开始报名

1. 只选择用户明确指定的一项活动。
2. 点击“开始报名”一次，观察按钮进入运行中/处理中状态。
3. 快速再次点击，确认不会启动第二场计划。
4. 等待计划完成或进入可读的失败状态；手机与电脑端都核对一次。
5. 如果响应超时，按 C5 的未知结果原则等待对账，不要重复开始。

**通过判据**：计划只启动一次，状态能从开始到完成/失败收口，已报名摘要与学校最终结果一致。

### D3：停止报名计划

1. 在计划确实运行时点击“停止”一次。
2. 确认按钮显示停止中并禁用重复点击。
3. 等待计划收口，确认后续不会继续提交。

### D4：取消待执行计划

1. 在存在待执行或待确认计划时点击“取消”。
2. 完成确认对话框；取消期间不要刷新到另一场计划。
3. 确认计划状态变为已取消，手机和电脑显示一致。

### D5：报名结果与重复报名保护

1. 报名成功后刷新手机页和电脑端列表。
2. 确认已报名摘要更新。
3. 再次打开同一活动时，确认界面不会鼓励重复报名，或服务端返回明确的已报名结果。

## 七、E 组：关窗、隐藏、托盘和手机唤回

### E1：窗口关闭四选与默认焦点

1. 点击桌面程序右上角 ×。
2. 在对话框打开时观察焦点是否落在“最小化到任务栏”这一安全选项。
3. 分别测试“先不关”“隐藏到后台运行”“最小化到任务栏”“直接退出”；每次先恢复程序再测试下一项。
4. 勾选“以后都这样”后关闭并再次打开，确认选择生效。
5. 有报名计划运行时再次点击 ×，确认仍会先询问，不直接中断计划。

### E2：隐藏门禁

1. 在托盘不可用且手机访问未开启时选择隐藏。
2. 确认程序保持可见，并出现“当前隐藏后无法找回”一类提示。
3. 开启 Tailscale 或确保托盘可用后再选择隐藏。
4. 确认窗口隐藏但程序继续运行，手机仍能刷新。

### E3：手机页唤回电脑窗口

1. 按 E2 隐藏窗口。
2. 手机打开“更多”里的“显示电脑窗口”。
3. 点击一次，等待结果。
4. 确认电脑窗口恢复可见，手机页仍保持连接。

### E4：记住选择的事务性

1. 先让隐藏门禁不满足，勾选“以后都这样”并尝试隐藏。
2. 确认隐藏被拒后，下次关闭仍会询问，不能直接沿用一条走不通的偏好。
3. 在门禁满足时成功隐藏并勾选“以后都这样”。
4. 再次关闭，确认记住的动作按预期执行。

### E5：长时间后台驻留

1. 选择隐藏或最小化，让程序后台运行至少 10 分钟。
2. 期间从手机刷新几次，确认通道和状态仍然可用。
3. 如果有报名计划窗口，在计划结束后再唤回电脑窗口。

## 八、F 组：Cloudflare 组件信任边界

这组在桌面程序上完成，目的是确认手机通道不会执行未经组件包校验的同名程序。

### F1：合法组件包正常工作

1. 确认 phone_control 组件已通过版本和哈希校验。
2. 开启 Cloudflare，完成 B3 的扫码配对。
3. 关闭通道后再开启一次，确认组件仍能启动。

### F2：组件文件被移走或替换后拒绝启动

1. 在程序已识别组件包的情况下，先关闭 Cloudflare。
2. 将组件包中的 `bin/cloudflared.exe` 临时移走，或替换成不同版本文件；不要删除整个组件目录。
3. 再次点击开启 Cloudflare。
4. 确认程序提示组件不可用，不启动隧道，不生成可用地址和二维码。
5. 恢复原文件后重新检测，确认功能恢复。

### F3：PATH 中的同名程序不能绕过校验

1. 在系统 PATH 或程序目录放置一个同名但未纳入组件包的可执行文件。
2. 重新检测并尝试开启 Cloudflare。
3. 确认仍按组件包缺失/校验失败处理；Tailscale 通道不受影响。

## 九、G 组：真实手机视觉与入口验收

### G1：手机页真实浏览器布局

1. 在真实手机浏览器打开配对页和主界面，分别观察竖屏和系统字体放大后的布局。
2. 确认状态栏、刷新按钮、今天卡、报名按钮、验证码区都不被裁切。
3. 确认主要按钮容易触摸，滚动时状态提示仍能看到。
4. 在断网场景下确认离线提示位于状态区域附近，而不是被页面底部内容遮住。

### G2：配对页与帮助入口

1. 在桌面帮助页找到手机访问入口，确认 Tailscale 和 Cloudflare 的定位说明清楚。
2. 确认二维码下方、配对成功地址下方、帮助页手机访问区都出现统一的书签提示。
3. 确认高级功能说明放在帮助/高级功能区域，入口与现有桌面 UI 风格一致。

### G3：状态文案颜色与含义

1. 在帮助页执行一次保存账号信息但不触发自动 OCR 的操作。
2. 确认成功提示使用信息色，不呈现为错误红色。
3. 触发真正的错误提示，确认错误色仍用于错误，不与成功提示混淆。

### G4：敏感信息显示边界

1. 查看手机页面、桌面帮助页和运行记录。
2. 确认不显示完整配对码、cookie、token、账号、密码和验证码。
3. 截图或提交证据前再次打码地址、二维码和任何会话信息。

## 十、H 组：校时自动重试与网络策略

### H1：启动时校时失败会自动重试

这项需要在不破坏系统设置的前提下制造一次短暂的网络不可用，例如程序启动时暂时断开网络，再恢复网络；不要修改系统时间。

1. 在网络不可用时启动程序，观察顶栏是否显示“未校准”并说明正在重试。
2. 恢复网络，记录后续重试时间，期望节奏为约 5 秒、10 秒、20 秒，之后约每 30 秒一次。
3. 校时成功后，确认顶栏恢复正常，活动列表可以加载，开始报名按钮不再被“待校准”锁住。
4. 继续观察 2 分钟，确认成功后不会继续无意义地重试。

### H2：学校请求与普通下载的网络路径

在有系统代理或环境代理的电脑上：

1. 执行一次学校状态读取或登录检查，确认业务请求仍能正常访问学校接口。
2. 执行一次更新检查或组件包下载，确认允许使用系统/环境代理。
3. 观察失败提示和运行记录是否能区分学校业务不可达与普通下载不可达。
