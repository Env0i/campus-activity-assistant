## 零点五、组件 Release 资产（2026-10-31 返修后新增，全部「未执行」）

单列一节，因为「本地 prepare 生成了组件 ZIP」与「GitHub Release 真的能下载到它」是两件事：
前者的自动化测试只能证明打包与校验逻辑，不能证明资产被上传。

| # | 动作 | 期望 | 结果 / 证据 |
|---|---|---|---|
| 1 | `tools/release.py --prepare` 产物目录 | 同时存在主程序 ZIP、独立 EXE、安装器、`manifest.json`，以及 `campus-activity-watch-phone-control-v<version>-win-x64.zip` | 未执行 |
| 2 | 检查 `manifest.json` 的 `files` | 含该组件资产，记录的字节数与 SHA-256 与 ZIP 实际值一致 | 未执行 |
| 3 | 正式发布后看 GitHub Release 资产列表 | 确实包含该组件 ZIP（不能只看发布器的「校验通过」输出） | 未执行 |
| 4 | 应用读取该 Release | `select_release_assets()` 选中组件，`resolve_phone_control_asset()` 返回 `state=available`；缺组件时仍返回 `no_component` | 未执行 |
| 5 | 真机点「下载并安装组件包」 | 进入校验并安装成功，不落到「这个版本没有发布手机控制组件」 | 未执行 |

**本返修前的根因（2026-10-31）**：`verify_release_assets()` 确实核验了组件存在、大小、哈希
与组件内部 manifest，但 `asset_digest()` 只计算 `zip/exe/installer/manifest` 四项，
`do_publish()` 传给 `publish()` 的最终上传列表也只有四项——「发布前门禁通过」因此不能证明
组件会被上传。返修把 `component` 补进资产指纹与上传列表，并用
`local/tests/test_lifecycle_release.py` 的 `test_asset_digest_includes_phone_component`
与 `test_publish_uploads_phone_component_asset` 两个用例锁住。

**结论口径**：以上五条在真实 Release 与真机完成前仍记「未执行」；不能用 1447 个本地测试
或假资产测试替代 GitHub Release 端到端证据。真实 `--prepare` / `--publish` 必须由用户显式确认。
