## R1 引导没有高亮框，只有压暗的遮罩

**现象**：五步引导第 1 步「这是活动时刻表」、第 3 步「核对计划」时，页面整体被压暗，
说明卡片落在底部居中，但目标区域（时刻表、右侧计划栏）**没有琥珀色高亮框**。

**期望**：遮罩压暗背景的同时，目标区域用高亮框圈出来；卡片放不下时可以落到底部，
但高亮框应该还在。

**根因**：`paintTour()` 在卡片上下都放不下时给 `#tour` 加 `is-bottom`，
而样式 `.tour.is-bottom .tour-spot { display: none }` 把高亮框一起隐藏了。
「卡片换位置」和「没有可高亮的目标」共用了同一个类，于是目标块一大（`#timetable`、
`#board`），卡片必然回退，高亮必然消失。

**位置**：`local/ui/views/tour.js` 的 `paintTour()`；`local/ui/styles.css` 的
`.tour.is-bottom .tour-spot`。

**证据**：`tour-step1.png`、`tour-step3.png`（两张都是遮罩在、无高亮框）。

**补充**：遮罩本身是好的——截图像素抽样显示背景被压到约 45% 亮度，说明 `tour-mask`
正常渲染；缺的只有 `.tour-spot`。

## R2 设置抽屉与原型不一致

**现象**：设置抽屉能打开、三组都在，但与原型
`design/prototype/workbench-2026-11/Main.dc.html`（`aside.draw` 那段）有多处出入：

| # | 原型 | 现行实现 |
|---|---|---|
| 1 | 手机控制、验证码识别都写「可选组件，约 18.4 / 31.6 MB。点"下载并安装"后自动下载、校验并启用，不会自动升级」 | 只写一句功能描述（「从外面查看活动和控制报名计划；只提供 Tailscale 与 Cloudflare 两种远程通道」），没有体积、没有「不会自动升级」 |
| 2 | 两组下面都有「下载和报名计划互不影响，可以关掉设置继续用」 | 没有这句 |
| 3 | 验证码识别右上是状态 chip（未安装 / 已启用），按钮是「下载并安装」 | 显示「已停用」+「启用验证码识别」（本机依赖已装、只是没启用） |
| 4 | 登录组标题「登录恢复」，账号密码直接展开在卡里 | 标题「保存的账号与失效后自动登录」，卡名「电脑续登录」，「填写账号密码」再展开 |
| 5 | 「关闭窗口时」顺序：每次询问 / 隐藏到后台 / 最小化到任务栏 / 直接退出 | 顺序：每次询问 / 最小化 / 隐藏到后台 / 直接退出 |
| 6 | 「关闭窗口时」说明：「选了直接退出也一样：报名计划运行中，关窗口前会先问你」 | 「点右上角关闭按钮时怎么做；计划运行中选『直接退出』仍会先问一次」 |
| 7 | 条款组标题「条款与隐私」 | 「使用条款与隐私」 |

**说明**：现行规范 `design/specs/assistance-panels.md` 是按实现写的，所以它和原型对不上
是「规范跟着实现走」的结果，不是实现漏了。要对齐哪一边需要用户定：
按原型改实现，还是承认实现为准、回改原型/规范。

**2026-11-04 用户口径（原话）**：「肯定是按照原型实现啊。我要求的是和原型 1：1 进行实现！
原型怎么写的就该怎么实现呗，然后原型没涉及到的设计就由我来提出。」

因此这一条的结论不是「两边选一边」，而是：**原型是 1:1 的实现基准**，实现向原型靠；
原型没写到的部分不由实现自行发挥，等用户提出。上面 7 处差异按这个口径都算实现偏差。

**待确认**：原型里有 6 处标着「演示：」的控件（下载失败、切换 Tailscale 状态、
手机配对成功、Cloudflare 隧道断开、下一次检查的结果、校验失败），看起来是原型的演示
脚手架而不是产品设计。这一条要不要也 1:1 搬进产品，需要用户明确；在确认前不实现。

**位置**：`local/ui/index.html` 的 `aside#settings`；`local/ui/views/settings.js`。

**全面比对**：R2 只是设置抽屉这一处。全界面的原型差距另见
[`prototype-gap.md`](prototype-gap.md)——四路并行比对，99 处，逐条标了「有没有书面依据」；
并排截图与 E 组对照表见 [`ui-gap/`](ui-gap/README.md)。

**证据**：`settings-advanced.png`（只截了「高级功能」，登录组里有打码账号，没截进来）。

## R3 「电脑续登录」把「未启用」写成「没装」

**现象**：设置 → 登录 →「电脑续登录」写：

> 验证码识别：没装，验证码要人工输入（电脑或手机上都行）。

但本机 `ddddocr` 是装着的（本机 Python 3.12 可导入），高级功能里也把它识别成
「已停用」并给了「启用验证码识别」按钮——也就是说**工具已经检索到了**，只是没启用。

**期望**：区分三态——已装且已启用 / 已装但没启用 / 没装。已装未启用时应写
「本机已装，还没启用」并指到设置里的启用按钮，不能写成「没装」。

**根因**：`views/phone.js` 用 `cred.ocr_ready`（后端 `feature_ready` = 已启用且可用）
当作「装没装」。后端 `_phone_relogin_setup()` 只回 `ocr_ready`，没有回「本机是否可用」。

**位置**：`local/ui/views/phone.js` 的 `ocrReady` 与 `#relogin-ocr-status` 文案；
`local/app.py` 的 `_phone_relogin_setup()`。

**证据**：截图未入库（登录组含打码账号），文案见上。

**附带结论**：不建议自动启用。启用这个组件等于允许「保存凭据 + 登录失效时自动登录」，
属隐私相关开关，保持用户主动开启；要改的是文案，不是默认值。

## R4 帮助页：副标题和快捷键说明与内容/原型不符

**现象 a（副标题）**：帮助对话框顶部写「使用说明、版本更新与本机数据」，但面板里只有
三步使用说明、键盘快捷键、使用条款；版本与数据早在 UI-B 就搬到设置里了。

**根因 a**：`#help-sub` 在运行时被 `paintHelp()` 用 `Api.help().subtitle` 覆盖，
而 `app.py` 的 `help()` 与 `store.js` 的 `DEFAULT_HELP.subtitle` 两处真源都还是旧文案；
`test_ui_contract` 的 `_EXPECTED_COPY` 也按旧文案钉着，所以两端一起漂移、测试不会红。

**现象 b（快捷键列表）**：帮助里列 4 条：F5 / Ctrl+F / Esc / Enter。原型列 5 条：
F5 / Ctrl+F / Esc / Tab（在按钮和活动之间移动）/ 空格（勾选或取消当前活动）。
实现里 `/` 也能跳到搜索框，但没写；Tab 与空格是浏览器原生行为，也没写。

**现象 c（Enter 的说明不准确）**：帮助写「焦点不在输入框时开始报名计划」。实际代码还会
在焦点落在 BUTTON / A 上时、以及帮助对话框打开时跳过，不会开始计划。照这句话操作
（例如刚点过「设置」按钮就按 Enter）不会得到描述的结果。

**位置**：`local/ui/index.html`（`#help-sub`、`.help-keys`）；`local/ui/views/help.js`；
`local/app.py` 的 `help()`；`local/ui/state/store.js` 的 `DEFAULT_HELP`；
`local/ui/app.js` 的全局 keydown（Enter 分支）。

**证据**：`help-shortcuts.png`。
