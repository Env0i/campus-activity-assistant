## 1. 每步可独立发布、行为不变、可单独回滚 —— 回答含糊

提案第 3 节给了规矩（「只改结构不改行为。全量测试通过、真窗口验过之后单独提交，方便回退」），按它自己的步骤核对：

- **拆 Api 五块（每块一提交）形式上可单独 revert，但「全量测试通过」的证据力不足。** prereq.md 第二节证实 42 个 app.X 补丁与 66 处 Api 成员改写在拆分后会悄悄落空（机制见判据 6）——测试绿不等于测到了真东西，独立发布的验收信号被削弱。
- **ESM 迁移步骤在序列里没有位置。** 第 2 节三步中没有「前端按功能分目录」，而待确认问题 1 说 ESM「随第 2 节『前端按功能分目录』那一步一起做」。混迁态（普通脚本与模块共存、经 window 挂载对象互调）经 esm-spike 证明可加载，但提案没把混迁态声明为「可发布态」，也没写补验（真机、打包）失败时的退路。
- **grab.py 最后动、先录对照测试——顺序判断正确**，是四步里唯一在「怎么证明行为不变」上有实质安排的；但对照范围未定义前（判据 7），「行为不变」仍不可证明。

**缺什么才算回答**：每步标注「行为变 / 结构变」并分别给提交规范；六条先修缺陷点名成清单（数目与 desktop.md 第七节的未修 5 + 部分 1 = 6 吻合，提案却没点名是哪六条）；ESM 步骤在三步序列中定序，并声明混迁态是否可发布、补验失败的退路。

## 总评

**现在不能直接开工——提案自己也没打算现在开工**：它把重构切法列为待用户定、把实现计划排在决策转入之后。按八条判据衡量，实打实的只有：五块的归块名字与 prereq 对得上、grab.py 放最后并先录对照测试的顺序、ESM 的 spike 证据与补验清单。工序级内容（文件集、终点值、红绿、回退、最坏情况、测试先行）全部缺位。

卡点按严重度排序：

1. **测试先行缺位（判据 6）**——42 补丁 / 66 改写没有迁移方案，拆 Api 的每一步「绿」都不可信，这是唯一会静默产出错误结论的卡点。
2. **切法未定（判据 1/2/7/8 的根）**——步骤划分在待定清单里，八条要求的每步属性连带悬空。
3. **量化终点缺失（判据 3/4）**——33/62/24 报数不定终点、无判定脚本，数字本身还未经本轮复核与对抗审计。
4. **Api 归块只覆盖一半（判据 5）**——跨块 24 与私有 93 无安置，无判据无反例。
5. **前端两步定序未定（判据 2）**——状态机与 ESM/分目录文件集全交叠。

值得肯定的：五份审计底座扎实（引用可复验、抽查留痕）；非目标把不动契约、不动登录态的边界划清；「待用户定」清单诚实。下一步应当是那份实现计划——每步一张表（文件集 / 行为变否 / 红绿 / 回退 / 最坏情况），并直接把 prereq 2.2 的按块补丁清单当判据 6 的工序原料。
