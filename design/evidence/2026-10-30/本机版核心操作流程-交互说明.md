## 0. 证据口径与阅读约定

| 记号 | 含义 |

| ✅代码 | 该行为在源码里可逐行追到，可作为实现契约 |

三条贯穿全局的架构事实（决定了下面所有门禁为什么存在）：

1. **前端是唯一状态持有者**：`local/ui/state/store.js:46` 的 `S` 是唯一状态容器，视图层不发桥接请求，只在 `render()` 里读 `S`（`local/ui/views/list.js:2-18`）。
2. **后端是最终防线**：条款（`local/app.py:653-672`）、登录四态（`local/app.py:1524-1538`，`result === "valid"` 是唯一放行条件）、已截止（`local/domain/plan_rules.py:64-84`）、冲突（`local/domain/plan_rules.py:87-98`）、busy（`local/app.py:2060-2068`）都会在 `start_plan` 内部再校验一次，前端门禁只是「让用户少走一步」，不是安全边界。
3. **同步 ack + 事件终态**：`check/list_activities/start_plan` 返回 `{ok:true,queued:true}` 之类的同步 ack，真正的结论由 `onBackend.check/activities/plan/task/plan_done/done` 事件送回（`local/ui/app.js:73-133`）。这条「两段式」是理解所有「正在确认…」「结果未确认」状态的前提。

## 2. 主流程链路（S0 → S9）

每一步统一四段：**前置条件 / 可操作项 / 被禁用项 / 系统反馈与下一步**，并给出失败分支入口（详见 §4）。

### S0 启动自检（窗口出现 → 首屏）

- **前置**：用户双击 exe / `python local/app.py`。WebView 页面与后端 `Api` 已创建。
- **可操作**：此时页面基本不可操作（15 秒内等桥接，`waitForBridge(15000)`）。
- **被禁用**：全部交互（桥未就绪时任何 `api()` 都会 reject「页面没有连接本机程序」，`local/ui/controllers/bridge.js:6-15`）。
- **系统做**（按序）：
  1. `api("bootstrap")` 拿一次性快照：`version/prefs/help/terms/business_clock/login/lifecycle/demo/retry_options/update_check/busy/plan`（`local/ui/app.js:14`、`local/app.py:675-726`）；
  2. `applyPrefs` 恢复筛选/策略/浏览器开关（`local/ui/controllers/refresh.js:2-33`）；
  3. `ingestTerms` — 若「未同意当前版 && 非 demo && 本会话没弹过 && 本机没拒绝过这一版」→ **立即自动弹条款**（`local/ui/controllers/terms.js:53-77`）；若 `terms.version` 缺失 → `markTermsUnknown()`，**不弹窗**，只挂横幅；
  4. `ingestBusinessClock` 落时钟结论；`setLogin(present, result...)`；
  5. `ingestBootstrapPlan` — 有运行中的计划就恢复任务表并置 busy、恢复「停止」入口；有终态计划就**只回放结论不重提**（`local/ui/controllers/refresh.js:59-90`）；
  6. 首次使用（`!prefs.welcome_seen`）与引导（`tour_version < 2`）**若被条款挡住则推迟**（`local/ui/app.js:44-55`），`runDeferredIntro()` 在同意后补跑（`local/ui/controllers/terms.js:140-149`）；
  7. `front_ready` → 起时钟轮询 → `refresh(true)` 静默刷新（`local/ui/app.js:64-69`）。注意 `refresh` 自身也过条款门（`local/ui/controllers/refresh.js:123-126`），所以**未同意条款时首屏不会发学校网络动作**。
- **下一步**：S1（条款未同意/未知）或 S3（已同意，直接进列表刷新）。

### S1 条款门

- **前置**：bootstrap 已返回 terms；`terms.unknown` 为 false。
- **可操作**：弹窗内「查看完整条款」「我已阅读并同意」「暂不使用」「关闭」(Esc/X)；横幅与帮助里的「查看条款」。
- **被禁用**：`btn-login`（`local/ui/views/board.js:746`）、`btn-refresh`（`:747`）、`btn-plan`（`:756`）、大屏快捷「登录」（`local/ui/views/board.js:227`）。**注意：活动行复选框不在条款门禁里**（`local/ui/views/list.js:137` 只用 `busy || !isEligibleForPlan`），也就是未同意时仍能勾选（纯本地状态、不触发网络动作），但开始被禁。
- **同意路径（严格自证）**：
  1. 提交的版本取**页面内嵌全文的版本节点**（`termsDocVersion()`，`local/ui/views/terms.js:132`），不是后端自报版本；
  2. 副本无版本 / 与 `S.terms.version` 不一致 → 本地拒绝，零请求零写入（`local/ui/controllers/terms.js:166-175`）；
  3. 置 saving，10 秒超时转「保存结果未确认」（`:179-183`、`:257-265`）；
  4. 回执必须 `version/accepted_version/accepted_at` 三项齐全且 `accepted_version === version`（`:211`），且 `docVersion === version`（`:220-225`），任一不满足**不解锁、不清 unknown**；
  5. 成功：清 `declined/unconfirmed`，落盘清 `terms_declined_version`，关窗，`refresh(true)` **最多补加载一次**，焦点回 `#btn-help`，恢复被让位的引导，跑被推迟的首屏引导（`:226-246`）。
- **拒绝路径**：「暂不使用」→ `declineTerms` 落盘 `terms_declined_version`（版本未知则不写空标记），关窗，**不退出程序**，横幅保留再同意入口（`local/ui/controllers/terms.js:329-342`）。保存中/未确认/只读查看时拒绝被忽略。
- **下一步**：同意 → S2/S3；拒绝或未知 → 停在「只能看帮助与条款」的受限态。

### S2 登录

- **前置**：条款已同意；无任务在跑（`!S.busy`）；后端额外要求「计划不是 ready/running」且非 demo（`local/app.py:1300-1316`）。
- **可操作**：「登录 / 重新登录」（`#btn-login`，`local/ui/views/login.js:99` 按状态切文案）、大屏快捷「登录」（`local/ui/views/board.js:227`）。
- **被禁用**：`S.busy`、组件缺失、条款门禁时禁用（`local/ui/views/board.js:746`）；后端在计划运行中直接拒「报名计划正在运行，先停止计划再登录」（`local/app.py:1300-1316`）。
- **系统做**：
  1. `S.login.preLoginSnapshot = loginSnapshotState()` 六字段快照（hours/ok/present/expireAt/savedAt/result，`local/ui/controllers/plan.js:315`、`local/ui/state/login.js:2-7`）；
  2. `setBusy(true)` + 胶囊「登录中…」+ 提示「请在弹出的浏览器中完成登录；取消或关闭窗口后会保留原状态」（`local/ui/views/login.js:29-33`）；
  3. 后端起 `login` worker，日志流进运行记录（`local/app.py:1316`、`:2178-2190`）；
  4. 结束发 `done{kind:"login"}`（`local/app.py:2204-2205`）。
- **成功**：作废快照 → 清旧锚点 → 结论卡「登录成功 / 正在加载活动列表」6 秒自动收起 → `doCheck()` + `refresh(true)`（`local/ui/controllers/plan.js:366-374`）。
- **失败/取消**：**整份回滚快照**（不把仍有效的旧会话画成失效），按 `loginFailCopy` 五类归因给「再试一次」（`local/ui/controllers/plan.js:375-384`、`:395-403`）。
- **下一步**：S3。

### S3 列表与登录四态

- **前置**：条款已同意。
- **可操作**：刷新（F5/按钮）、筛选六键（`#q/#time/#sort/#checkin/#checkout` + 状态芯片）、行点击展开地点、帮助。
- **被禁用**：刷新在 `listState==="loading"` 或条款未同意时禁用（`local/ui/views/board.js:747`）；活动行按「已截止/已报名/busy」逐行禁用复选框（`local/ui/views/list.js:137`）。
- **系统做**：`check` 与 `list_activities` **两条独立分支**同轮发起，各自带 request_id 与代次（`local/ui/controllers/refresh.js:127-134`）；`check` 结论落 `S.login.result`（`local/ui/app.js:88-89`），`activities` 结论落 `S.items` 并合并本地 120 秒窗口内的已确认成功（`local/ui/controllers/refresh.js:366-402`、`local/domain/plan_rules.py:101-130`）。
- **空态四分**（学校成功返回 0 场时）：`checking`「正在检查登录状态」/`none`「登录后查看活动」/`expired`「登录状态失效，先重新登录」/`unknown`「暂时无法确认登录状态」/`valid`「学校当前没有返回活动」（`local/ui/views/list.js:195-201`、`:258-287`）。
- **下一步**：`valid` → S4；`none/expired` → S2；`unknown` → 刷新重试（**不得诱导重登**）。

### S4 选择

- **前置**：列表 `ready`，非 busy。
- **可操作**：勾选/取消、整行点击（地点格除外）、「下一场」快捷选择（大屏 `#btn-board-pick` → `toggleSelection(nextOpen().bestId)`，`local/ui/app.js:217-220`）、「清空选择」。
- **被禁用**：已截止、已报名、busy 时复选框禁用（`local/ui/views/list.js:137`、`local/ui/state/filters.js:229`）；条款未同意时**仍可勾选**（见 S1 注）。
- **即时冲突拦截**（不静默替换）：与已报名活动重叠 → 「与已报名活动「X」的举办时间重叠…不能再加入计划」；与本次已选重叠 → 「与「X」的活动时间重叠，同一计划只能选择其中一场。**已保留原选择**」（`local/ui/state/filters.js:242-257`）。
- **检查条**（只提醒不硬挡）：网络断开、登录估算过期、北京时间待校准/上次校准、0=直到截止但缺 sign_end「本次最多 2 分钟」、开放在 24 小时以后（`local/ui/views/board.js:247-283`）。
- **下一步**：S5。

### S5 开始计划（含「开始请求对账」子状态机）

- **前置**：§1 全部门禁 + 北京时间可读 + `listState==="ready"`。
- **可操作**：策略下拉「尝试时长」「最多提交次数」、「显示浏览器窗口」、「开始报名计划」、清空选择。
- **被禁用**：`canStart` 不满足即禁用；文案随状态切 `计划运行中 / 正在确认是否启动… / 正在提交… / 北京时间未校准 / 开始报名计划`（`local/ui/views/board.js:756-765`）。
- **提交**：`startPlan()` 用 `newRoundId("start")` 生成 request_id，15 秒对账定时器，`api("start_plan", items, headed, {retry_for_s,max_attempts}, requestId)`（`local/ui/controllers/plan.js:35-48`）。
- **结果分支**：
  - `res.pending`（去重命中在途）→ 不重发，转对账（`:52-57`）；
  - `res.error==="terms_required"` → 回到条款门禁（`:63-66`）；
  - `res.error ∈ RUNTIME_ERRORS` → 只挂组件横幅，不弹同义结果框（`:67-74`）；
  - `{ok:false}` 业务失败 → `showPlanError(text, conflicts, errors)`（`:75`）；
  - 成功 ack → 记 `plan_generation`，建立/推进 `S.plan`，`setBusy(true)`，日志「已安排 N 场活动：X 场预报名等开放，Y 场立即报名马上执行」（`:81-107`）；
  - **终态早于 ack**（15 秒内就跑完的计划）→ 保持终态呈现、不置忙，避免「永远不结束的运行态 + 点不动的停止按钮」（`:89-97`）。
- **对账子状态机**（`reconcileStart`，`:127-201`）：
  ```
  submitting --15s 无 ack--> reconciling
  reconciling --start_request_state-->
     accepted -> adoptPlan（恢复任务表/停止按钮；终态直接 presentPlanDone）
     rejected -> showPlanError
     canceled -> 「这次开始已取消」
     pending  -> 2s 后重试（最多 8 次）
     无回应/超时(5s) -> unknown：「结果未确认，请勿重复启动」+「重新确认」
  ```
  关键约束：**绝不重发 `start_plan`**（`:117-119` 注释）；unknown 态保持开始按钮禁用，只留只读确认入口（`:146-158`）；旧代次迟到回执不得落到新计划上（`:168`）。
- **下一步**：S6。

### S6 运行中

- **前置**：计划 ack 已到，`S.plan.status ∈ {ready, running}`，`S.busy=true`。
- **可操作**：停止（`#btn-stop`）、**按场取消未提交任务**（任务卡行内「取消」，仅 `queued/waiting` 且 busy 时出现，`local/ui/views/board.js:685-686`）、展开运行记录、关闭窗口。
- **被禁用**：登录、开始、清空选择、行复选框、筛选刷新（`local/ui/views/board.js:746`、`:756`、`:768`、`:772`）；引导暂停（`local/ui/views/login.js:107-114`）；大屏动作区整组隐藏（`local/ui/views/board.js:217-223`）。
- **运行模型**（单一来源 `executionView()`，`local/ui/state/task-display.js:89`）：`phase ∈ {idle, preparing, waiting, arming, submitting, settling}`；大屏文案/LED/倒计时/路线图全部读同一份（`local/ui/views/board.js:297-404`）。
- **每场任务卡**：等待/准备/提交/成功/已报名/失败/取消；提交中显示「已提交 N/M 次」或「已提交 N 次（不限次数）」+最近原因+「重试到 HH:MM」（telemetry 优先，其次 `effectiveRetryDeadline` 推导，`local/ui/views/board.js:628-655`、`:705-734`）。
- **路线图五站点**：本次启动 / 活动页已打开 / 开始监测 / 原定开放 / 本次尝试截止；**只认真实 checkpoint，没发生就显示「待启动/待打开/待开始/待定」**（`local/ui/views/board.js:338-380`）。
- **计划完成前不发全局结论**：单场终态只更新任务卡与日志（`local/ui/controllers/plan-events.js:107-120`），整屏结论等 `plan_done`。
- **下一步**：自然结束 → S8；用户停止 → S7。

### S7 停止（二次确认 → 正在停止 → plan_done）

- **前置**：计划 ready/running，`!S.stopping`。
- **可操作**：「停止」→ 弹 `#dlg-stop`（`local/ui/controllers/plan.js:275-280`）。
- **二次确认文案**：「工具将停止后续尝试。已提交的请求仍可能成功，停止计划不会取消已成功的报名。」两个出口：`继续计划`（value=no）/ `停止计划`（value=yes，`local/ui/index.html:283`）；Esc = 关闭 = **不停止**（只有 `returnValue==="yes"` 才走 `doStopPlan`，`local/ui/app.js:226-231`）。
- **停止执行**：置 `S.stopping=true`（胶囊 note「正在停止计划；已报名的场次不受影响」，`local/ui/views/login.js:19`）→ 按钮文案「正在停止…」并禁用（`local/ui/views/board.js:766-767`）→ 日志「正在停止计划：结束还在重试的场次…」→ `api("stop_plan", plan_id)`（`local/ui/controllers/plan.js:282-303`）。
- **后端**：`stop_plan` 幂等 → 协调器 `stop()` 全员唤醒，`queued/waiting` 立刻标 `canceled`「计划已停止」，然后 `_terminate_plan_procs()` 按进程树 `taskkill /F /T`（`local/app.py:1733-1750`、`local/signup_plan.py:386-403`）。
- **停止的语义边界**（必须原样告知用户）：
  - 已确认成功 / 已报名 → 不变；
  - 已发出但没回应的提交 → 任务 `failed` 且 `stop_reason=unconfirmed`「已按你的要求停止；最后一次提交没有拿到确定回应」，次数不归零，**并列入「待核对」**；
  - 还没提交过的 → `canceled`，`stop_reason=user_stopped`；
  - 取消晚到但 worker 已给确定终态 → 按那个结论记，不降级成取消（`local/domain/plan_rules.py:164-182`）。
- **收尾**：`plan_done` 到达才解锁 busy（`local/ui/controllers/plan-events.js:2-13`），结论卡「报名计划已停止 / 已提交的场次保留原状态，尚未提交的场次已取消」+「重新选择活动」→ `restartStoppedPlan()`（只把 canceled/failed 且仍可报的场次重新选上，`local/ui/controllers/plan-events.js:42-49`、`:87-98`）。
- **下一步**：S8（结果）/ S4（重新选择）。

### S8 结果与重载恢复

- **前置**：`plan_done` 到达，或窗口在计划运行/结束后被重载/重开。
- **可操作**：结果卡动作（刷新列表 / 重新选择活动 / 再试一次）、逐场任务卡、运行记录、去学校活动页核对。
- **五种终态结论**（`local/ui/controllers/plan-events.js:2-67`）：

| 计划状态 | 结论卡 | 关键文案 |
|---|---|---|
| `completed` | ok，「报名计划完成」 | 「已报名 N 场，建议去学校活动页确认一眼。」 |
| `stopped` | partial，「报名计划已停止」 | 「已提交的场次保留原状态，尚未提交的场次已取消。」+ 未知场次并列 + 重新选择 |
| `partial` | partial，「报名计划部分完成」 | 计数器串 `已报名 N 场 · 报名未成功 N 场 · 待核对 N 场 · 未提交 N 场 · 已取消 N 场` |
| `failed` 且含未知 | partial（中性），「报名计划已结束，有 N 场需确认」 | 不能把所有场次说成「都没抢到」 |
| `failed` 干净 | bad，「报名计划没有成功」 | 失败场次 + 到达的停止条件（次数/时长/截止） |

- **两类「未知」绝不合并**：`unconfirmed`（已提交没拿到确定回应，本工具不会自动重发）/ `auth_unavailable`（登录状态无法确认，本场没提交）——`planOutcome()` 分列，`unknown` 只是两者之和（`local/ui/state/plan.js:101-128`）。
- **重载恢复**：`bootstrap.plan` 快照 → `ingestBootstrapPlan`：运行态恢复任务表 + 置 busy + 恢复停止入口；终态走**与 `plan_done` 同一个呈现入口**，不重发、不重复日志、不自动刷新（`local/ui/controllers/refresh.js:59-90`、`local/ui/controllers/plan-events.js:2`）。`plan_generation` 保证旧计划的迟到事件不改写当前计划（`local/ui/controllers/plan-events.js:71`、`local/ui/state/plan.js:54-96`）。
- **下一步**：S9 或 S4。

### S9 重登 / 会话变化回环

- **触发**：胶囊显示「登录已失效」；或用户主动「重新登录」；或登录成功后事件驱动的 `check`。
- **前置**：同 S2（无任务在跑）。
- **系统做**：`preLoginSnapshot` 快照 → 登录 → 成功则换新锚点并 `doCheck()`；失败/取消/超时整份回滚（`local/ui/controllers/plan.js:305-384`）；结论变化统一经 `syncLoginDependentView()`（胶囊+时钟+空态+整屏）收口（`local/ui/state/login.js:65-70`）。
- **登录胶囊状态机**（`local/ui/views/login.js:2-105`，分支先后即优先级）：

| 显示 | 触发条件 | note / 下一步 |
|---|---|---|
| `已登录/未登录`（is-busy） | `S.busy && !loginPending` | 「登录状态保持不变；计划进度见报名区域」 |
| `演示模式/内存样例` | `S.demo` | 「不读取登录信息、不访问学校」 |
| `登录中…` | `loginPending` | 「取消或关闭窗口后会保留原状态」 |
| `检查登录…` | `checking`（或 ok===null 且有会话与估算） | 「正在检查登录状态，马上就好」 |
| `未登录` | `present === false` | 「点右上角「登录」，在打开的浏览器中完成登录」 |
| `登录待确认` | `result==="unknown" && ok===false` | 「检查网络后点「刷新」，**先不用重新登录**」 |
| `已登录`+「估算已到点」 | `result==="valid"` 且 `h<=0` | 「估算时间只是提醒，不代表失效」 |
| `登录已失效` | `ok===false` 或 `h<=0` 且 `present!==false` | 「重新登录后可继续使用」 |
| `已登录`+「约剩 N 小时」 | `h<=2` 橙色 / `h>2` 绿色 | 「不到 2 小时，建议现在先重新登录一次」 |

- **下一步**：登录有效 → S3/S4。

## 3. 主链路状态机（文字版，便于直接画图/写测试）

```
[启动] --bootstrap--> (bootstrap失败) -> TERMS_UNKNOWN
                    \-> (terms未同意) -> TERMS_LOCKED --同意--> (首屏refresh)
                                       \--拒绝--> TERMS_DECLINED(停用;可再看条款)
(首屏refresh) -> LIST_LOADING -> {checking/valid/expired/unknown/none}
   none/expired -> LOGIN ->{成功->CHECK->LIST ; 失败/取消->回滚->原态}
   unknown -> (点刷新) -> LIST_LOADING
   valid   -> LIST_READY -> SELECT -> START_SUBMITTING
START_SUBMITTING --ack accepted--> PLAN_READY -> PLAN_RUNNING
   |--terms_required--> TERMS_LOCKED
   |--组件错误--> COMPONENT_DOWN(横幅; 只有刷新可恢复)
   |--业务失败--> LIST_READY(结论框)
   \--15s 无 ack--> START_RECONCILING --accepted--> PLAN_RUNNING/PLAN_TERMINAL
                                        |--rejected--> LIST_READY(结论框)
                                        |--canceled--> LIST_READY(「这次开始已取消」)
                                        |--pending x8 / 5s 超时--> START_UNKNOWN(禁止重复开始,只读确认)
PLAN_RUNNING --任务逐个终态/取消--> ... --plan_done--> PLAN_{completed|partial|failed|stopped}
PLAN_RUNNING --停止(二次确认)--> STOPPING --plan_done--> PLAN_STOPPED
任何态 --窗口重载--> bootstrap.plan 快照: running->恢复busy/停止入口 ; terminal->只回放结论
任何态 --关闭重开--> 生命周期 ui.json 记 run_open/心跳; 关闭时长 clean/abnormal/unknown
```

**计划与任务状态取值**（文档与实现一致）：计划 `ready|running|partial|completed|failed|stopped`（`local/ui/state/plan.js:15`）；任务 `queued|waiting|submitting|success|already_signed|failed|canceled`（`local/ui/state/plan.js:16`、`local/signup_plan.py:333`）。终态集合 `TASK_TERMINAL` 不含 `waiting/queued/submitting`，所以「已终态的任务不会被旧进度拖回运行态」（`local/ui/state/plan.js:85-88`）。

## 4. 分支与异常（E1–E14）

### E1 条款拒绝
- 触发：「暂不使用」或条款弹窗 cancel。

- 出处：`local/ui/controllers/terms.js:329-342`、`local/ui/views/board.js:786-792`、`local/ui/app.js:190-204`。
- 可验证性：✅代码可追；✅可用「拒绝→重开程序」验证跨重启仍不弹（依赖 `terms_declined_version` 落盘，`:68-69`）。

### E2 条款未知 / 版本不符 / 保存回执不可确认

- 表现：横幅「条款状态没能确认。」（不自动弹窗）；保存中按钮禁点、Esc/X 被拦；超时后文案「保存结果未确认…门禁保持关闭」+「重新确认状态」。
- 恢复：只在弹窗内点「重新确认状态」→ 只读一次 `bootstrap` 快照，按三项齐全 + 副本匹配才解锁（`local/ui/controllers/terms.js:269-325`）。读不到就继续保持关闭。
- 出处：`local/ui/controllers/terms.js:38-48`、`:158-252`、`:257-265`、`:269-325`。
- 可验证性：✅代码可追；⚠️「bootstrap 失败」真实触发需断桥，只能靠注入/测试桩。

### E3 从未登录（`none`）

### E4 登录失效（`expired`，仅 4001）

### E5 登录未知（`unknown`）——最容易做错的一条
- 触发：网络失败、超时、组件缺失（`err_code` 一压成 unknown，`local/application/login_service.py:29-31`）。
- 表现：胶囊「登录待确认」，「检查网络后点「刷新」，**先不用重新登录**」；空态「暂时无法确认登录状态」。

- 可验证性：✅可真实复现（打开登录窗直接关掉）；`10 分钟` = worker `--timeout` 默认 600 秒（`local/grab.py:2998`，`local/app.py` 登录分支不传该参数），文案在 `local/grab.py:864-865` 与 `local/ui/controllers/plan.js:398`；等满 10 分钟的真实等待未实测 → 见 §7 V6。

### E11 停计划（二次确认 + 在途语义）

### E13 重试扩窗（三种模式 + C01 缺口）
- 三种模式（`local/domain/retry_window.py:5-12`、`:23-27`）：
  - 正数（120/600/1800/3600）= **硬承诺**，显式 `--retry-for`，扩窗整条不生效（`local/application/plan_service.py:58-69`、`local/grab.py:1323`）；
  - `-1` 自动延长 = 只给 `--window 120`，404/429 连击时 `window_extended` 逐次扩到 **起点 + 25 分钟**（`ADAPTIVE_SECONDS=1500`），`sign_end` 仍硬截（`local/grab.py:1541-1548`、`local/application/plan_service.py:109-115`、`:188-208`）；
  - `0` = 直到报名截止，缺 `sign_end` 回退 120 秒，不扩窗（`local/domain/retry_window.py:45-60`）。
- **C01/RISK-001 未解除**：提交监听窗口覆盖整个提交阶段，页面自发的同路径请求会被误计，因此「看到报名成功」≠「本次点击导致成功」；`docs/RETRY_POLICY_GUIDE.md:125-182` 明确标 `blocked/unproven`，发布阻断未解除。
- 界面口径：`effectiveRetryDeadline` 优先 telemetry 的 `retry_deadline`，其次按 `retry_started_at` 冻结锚点推导，**锚点不随墙钟跨过开放时刻而切换**（`local/ui/views/board.js:705-734`）。
- 可验证性：❌真实扩窗需学校侧 404 连击；单测层面可验（`local/tests/`）。桌面能否选到 `-1` 见 C1。

## 6. 文档 ↔ 实现冲突（按严重度排序）

### C1【高】重试「自动延长（-1）」在桌面端**可选但选不上**
- 文档：`docs/UI_SPEC.md:235` 只列 2/10/30 分钟、1 小时、直到报名截止 **5 项**；`docs/RETRY_POLICY_GUIDE.md:225-231` 却又写了三种模式含 `-1` 自动延长 → 文档内部不一致。
- 实现：
  - `local/ui/index.html:55` 渲染了第 6 个选项 `<option value="-1">自动延长（最多25分钟）</option>`；
  - 但 `local/ui/app.js:259-266` 的 change 白名单是 `["120","600","1800","3600","0"]`，**不含 `"-1"`** → 选中后走 else 分支 `event.target.value = String(S.retryPolicy.retry_for_s)`，**静默回滚**成旧值；
  - 后端与 worker 完整支持 `-1`（`local/domain/retry_window.py:27`、`local/application/plan_service.py:61-69`、`:109-115`、`local/grab.py:1204-1205`、`:1541-1548`）；
  - 手机页没有这个白名单，`Number($("retry-for").value)` 直接保存，且选项由 bootstrap 的 `retry_options.choices` 填充（`local/ui/m/app.js:504-508`、`local/app.py:159-177`）→ **同一份 prefs 两端不一致**。
- 影响：桌面用户点「自动延长」看起来选中又跳回；扩窗到 25 分钟在桌面真实链路**不可达**（只能由手机页写入 prefs 或手工改 `ui.json` 后，桌面 `applyPrefs` 才会把它显示出来——`local/ui/controllers/refresh.js:16-22` 的白名单取自后端 choices，所以显示层是支持 `-1` 的）。
- 建议：把 `"-1"` 补进 `local/ui/app.js:261` 白名单（或改成「用 `S.retryOptions.choices` 派生白名单」，与手机页同源），并同步补 `docs/UI_SPEC.md:235`。

### C2【中】`start_plan` 签名与「开始请求对账」两个 API 未进 §5.1 方法表
- 文档：`docs/UI_SPEC.md:113` 写 `start_plan(items, headed)`；`docs/UI_SPEC.md:237` 写 `start_plan(items, headed, retry_policy)`。
- 实现：`local/app.py:1430` 是 `start_plan(items, headed=False, retry_policy=None, request_id="")`（四参）。
- 方法表缺项：`start_request_state`（`local/app.py:1376-1409`，前端 `local/ui/controllers/plan.js:166` 与手机页 `local/ui/m/app.js:364` 都调用）和 `cancel_start_request`（`local/app.py:1411-1429`，**桌面与手机都没有 UI 入口**）不在 §5.1 方法表里；`request_id` 参数也只字未提。
- 但语义并非全无出处（初稿误判，此处更正）：`docs/UI_SPEC.md:378-381`「失联可恢复且不重复报名」已写明 `start_plan` 带 `request_id` 幂等、15 秒无响应转「正在确认是否启动」、只调 `start_request_state` 对账、accepted 恢复任务；`:369` 还写了「接纳以本进程缓存为准」。缺的只是**接口契约层**（方法表与签名）。
- 影响：只读 §5.1/§5.8 的实现者会按三参签名写调用、漏掉幂等键与对账方法，导致「15 秒无响应」时可能二次启动（正是 `local/ui/controllers/plan.js:32-34` 注释想避免的事故）。
- 建议：§5.1 方法表补 `start_plan(..., request_id)`、`start_request_state`、`cancel_start_request`（并注明后者当前无 UI 调用），与 `:378-381` 的语义段落交叉引用。

### C3【中】「停止 ≤ 1 秒」是界面承诺，不是后端保证
- 文档：`docs/UI_SPEC.md:228` 写 `stop_plan` 先置停协调器再 `taskkill /F /T`，「≤1 秒」。
- 实现：`stop()` 同步置 canceled 确实很快（`local/signup_plan.py:386-403`），`_terminate_plan_procs` 立即杀树（`local/app.py:1745-1750`）；但 `plan_done` 要等任务线程 `finally` 收尾，收尾链里有 `reader_done.wait(1.5)`、`proc.wait(timeout=5.0)`、必要时再 `wait(2.0)`（`local/application/plan_service.py:295-313`），协调器还要 `_join_threads` 等全部落定（`local/signup_plan.py:465-472`）。
- 影响：最坏情况下 busy 解锁可远超 1 秒；界面文案是「正在停止…」并保持 busy（与文档一致），但**不要把它当 SLA 写进验收用例**。
- 建议：文档改成「立即停止新尝试；进程树终止与终态收口通常 1 秒内，最坏受 worker 收尾等待上限约束（约 1.5–7 秒）」。

### C4【中】条款未同意时**活动仍可勾选**，文档表述易被读成「列表不可操作」
- 文档：`docs/UI_SPEC.md:136-147` 与 `local/ui/views/board.js:788-791` 的横幅都写「登录、活动列表和报名计划保持停用」。
- 实现：复选框禁用条件只有 `S.busy || !isEligibleForPlan(item)`（`local/ui/views/list.js:137`、`local/ui/views/board.js:769-773`），不含 `termsGate`；`toggleSelection` 也只挡 busy/不合格（`local/ui/state/filters.js:225-229`）。
- 影响：用户能在未同意条款时勾选活动，但点开始会被拦回条款门禁（`local/ui/controllers/plan.js:5-8`、`local/ui/controllers/refresh.js:123-126`）——行为安全，但与「列表停用」的字面表述不符。
- 建议：二选一——要么把 `termsGate` 并进复选框门禁，要么把文案改成「登录、加载活动列表与开始报名计划停用（可先浏览/预选）」。

### C5【低】§5.13 的「说明/更多」双入口是历史层，已被 §5.15 取代
- `docs/UI_SPEC.md:292-305`（§5.13）仍描述旧双入口；`docs/UI_SPEC.md:334+`（§5.15）与实现都只有单一帮助入口（`local/ui/index.html:21`、`local/ui/app.js:170`、`:289`）。
- 影响：新同学读 §5.13 会去找不存在的「说明」按钮。建议在 §5.13 加一句「入口部分由 §5.15 取代」。

### C6【低】§5.1「只有 bootstrap()/help() 可 await」的措辞与 JS 侧不一致
- 文档意图是「其它方法只回 ack，结论走事件」；实现里 `api()` 一律返回 Promise（pywebview 桥），前端大量 `.then/.catch`（如 `local/ui/controllers/refresh.js:164-194`）。
- 影响：不影响行为，但容易让前端误以为 `check()` 的返回值就是结论。建议措辞改为「只有 bootstrap()/help() 在返回时就是完整结果；其余方法的返回值只是 ack」。

### C7【低】已确认没有冲突的两处（避免开发重复排查）
