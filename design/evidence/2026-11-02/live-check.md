## 二、第 2 项：用 307 场数据回答

把 307 场的 `act_start`（活动开始）与 `sign_end`（报名截止）逐条比：

| 比较 | 场次 |
|---|---|
| `act_start < sign_end`（活动已开始、报名还没截止） | **0** |
| `act_start == sign_end` | 8 |
| `act_start > sign_end` | 299 |
| `checkin_start < sign_end`（签到先于报名截止） | **0**（292 场有签到时间） |

差值分布：最小 0 小时，中位 1.5 小时，最大 464 小时。

## 四、第 9 项：17.5 小时是常量，不是实测

- `local/app.py:102` `TOKEN_LIFETIME_H = 17.5`
- `local/gui.py:40` `TOKEN_LIFETIME_H = 17.5     # 实测寿命，仅用于显示「约剩几小时」`
- `local/grab.py:906` 登录成功时打印「有效期约 17 小时」

三处都是写死的数字，运行时不测量、不更新。今天登录时程序同样打印「有效期约 17 小时」。
所谓「17.5 小时」是一次观测被固化进代码的常量，界面上「约剩 N 小时」是按这个常量倒推的，不是按 token 真实过期时间算的。
桌面端这一份 `server/reports/` 里没有 `token-lifetime.md`（只有 10-19 到 10-21 的每日报告）。
但**服务器上是有的**：最近一次生成于今天 12:09，4 枚 token 最长观测 12.2 小时未失效，
另有 9 枚 token 在 12 分钟到 2 小时之间就失效——**不是固定 TTL**。
详见 `server-live-check.md` 第三、四节。

补一条现场证据：刚登录不久打开真实界面，右上角徽标写的是「已登录　**剩余时间未知，建议重新登录**」

## 十五、手动点击对照：人点一次，页面发什么（第 3 项，18:42）

做法：带桌面端登录态的 headed 浏览器打开活动详情页，页面里注入点击监听、进程侧监听
request/response，人点「立即报名」→「确定」。只记条数、请求形状、hash 长度、状态码与
code/message，不导 HAR，不落 header/body。

观测对象：(男生)宿舍文化--查寝--11.4，`45362856a8484b33ba9c9902f0c45148`
（16:57 起名额已满，所以这次点击预期就是失败）。

起点 18:42:29 打开页面，18:42:37 首屏 32 个请求结束，开始静置。

```
18:42:59 [signUp] #1 GET /dr/api/rjyHdCyr/signUp/02965ed1…696e9 无参数
18:42:59 [signUp响应] status=200 code=500 message=报名人数已满
18:42:59 [点击] 第 2 次：确定
```

结论：

1. **静置不发**。22 秒里 0 条；连同 13 节的两轮 30 秒、14 节的 20 秒，共 5 次静置都是 0 条。
2. **点击才发，而且只发 1 条**。「立即报名」+「确定」两次点击合起来只产生 1 个 signUp。
3. **请求形状是 GET，hash 在路径里，不在 query、不在 body**：
   `/dr/api/rjyHdCyr/signUp/<hash>`，路径参数 `无参数`（query 为空）。
4. **hash 长度 96**，与直发那条的参照长度完全一致 → 直发复刻的就是这条请求（差别只在方法：
   页面用 GET）。
5. 页面点击路径同样拿到 `code:500 报名人数已满`，与 14 节程序提交的返回一致。

记错一处，留档说明：日志里那行「signUp 出现时前后 8 秒内没有点击 —— 页面自己发的」是错的。
脚本用「最近一次检测到的点击」判断，而轮询有 1 秒延迟，请求先于判定执行；按时间戳人工核对，
点击与请求同一秒（18:42:59，`[点击] 第 2 次：确定`）。

另有一条同样形状的请求出现在 18:42:06（上一轮窗口，启动后 7 秒）。那一轮点击监听注入在
页面跳转之前被清掉了，没有点击记录，**无法判定来源，未计入任何结论**。

补一条当场核对（离线算，不联网）：

```
build_signup_hash('45362856a8484b33ba9c9902f0c45148', 1762000000000) -> 96 位
build_signup_hash('45362856a8484b33ba9c9902f0c45148', 1793616244733) -> 96 位
```

`local/signup_signing.py:135 def build_signup_hash(activity_id, epoch_ms)`：
明文 `f"{activity_id},{epoch_ms}"` → PKCS7 → AES-128-ECB（key 见 `signup_signing.py` 内
`_SIGN_KEY`，不复制到文档）→ 小写 hex。长度只由明文长度决定（每块 32 位 hex），
所以「96」不是固定值，但页面这条与直发这条在这场活动上都是 96，**算法、key、明文结构一致**：
页面与直发是同一个签名，差别只在时间戳。

顺带一处注释与实际不符，留给文档修订：`local/grab.py:2144` 注释写「hash 不含活动 ID」，
但明文第一段就是 `activity_id`——准确说法是「**URL 里**不含活动 ID」，不是 hash 里不含。

## 二十六、日志系统的缺口清单（希望有完整的日志系统）

按「能不能事后回答一个具体问题」来判，现有日志做不到下列七件事：

| # | 缺口 | 现状 | 后果 |
|---|---|---|---|
| 1 | 关键动作不落盘 | 登录、条款同意、token 刷新只 `print` 或只进界面 | 关键状态变化无痕（第 25 节） |
| 2 | 失败没有原始原因 | `check` 失败只写 `stop_reason=login_invalid` | 分不清真 401/4001 与网络抖动 |
| 3 | 没有来源标识 | 不知道哪条路径、哪个进程发起 | 桌面端/界面/服务端三处动作混在一起 |
| 4 | 没有级别 | 全靠 `[i] [X] [!] [retry]` 前缀 | 无法按严重程度筛选 |
| 5 | 没有轮转与上限 | 每行 `open(..., "a")` 写一条即关，无切分 | 6 天 1 MB，一年 60–90 MB，且历次运行混在一份文件里 |
| 6 | 写失败静默 | `except Exception: pass` | 日志丢了你也不会知道 |
| 7 | 两套格式互不相通 | 桌面端 `grab.log` 带时间戳；服务端 `data/cron.log` **无时间戳、无日期** | 「最近 7 天按日统计」在服务端给不出，只能改用 journald |

由此提出的需求（**产品侧，不是本次采集内容**）：

- 每条日志固定字段：时间（北京时间）、级别、来源（cli / gui / auto_relogin / server）、活动 ID、事件名、原始错误文本；
- 登录类动作必须落盘，含**发起方**与**耗时**（人工要打字，秒级到几十秒；自动化通常几秒），足以区分人工与自动；
- 日志按天或按大小切分并保留 N 份，永不静默吞异常（写失败至少打到 stderr）；
- 桌面端与服务端用同一套格式，便于合并分析。

## 二十八、直发实测：一次真实报名成功（2026-11-03 10:00）

目标：活动 A（本人报名的一场，名称与 ID 已隐去），报名窗口 11-03 10:00:00 → 11-04 14:59:59，活动 11-04 18:00–19:00（地点已隐去）。

链路（全部直发，不经页面）：`POST /upms/security/runtime/profile` 取 16 位运行时密钥 → 自算 `AES-128-ECB-PKCS7("{活动ID},{毫秒}")` → 96 位 hex → `GET /rjyHdCyr/signUp/<hash>`，请求头只带 `Accept`/`token`/`Referer`/`User-Agent`。

| 次数 | 时刻 | HTTP | 耗时 | `code` | `message` |
|---|---|---|---|---|---|
| #1 | 09:59:59 | 200 | 296 ms | 500 | 报名未开始！ |
| **#2** | **10:00:01** | **200** | **1139 ms** | **1** | **操作成功！** |
| #3–#42 | 10:00:03–10:00:59 | 200 | 240–1754 ms | 500 | 活动时间与已参与活动时间冲突：<活动 A> |
| #18 | 10:00:32 | — | — | — | `ReadTimeout(read timeout=8)` |

复核（10:01 `list --all --json`）：`signed=true`、`state=已报名`，账号已报名总数 13 → 14。

结论：

1. **运行时密钥链路可用**。密钥由登录态下发，不依赖任何静态常量，96 位 hash 被服务端接受（错钥会在解密阶段失败，不会走到业务判断）。
2. **成功码是 `code=1`**（`操作成功！`），与 `local/grab.py` 的 `_apply_conclusion` 判定一致；`code=0` 在本链路里反而对应「版本不兼容」那条特殊语义。
3. **早 1 秒就拒**：09:59:59 的请求拿到 `报名未开始！`。服务端严格按 `sign_start` 卡，提前打没有余量。
4. **重复提交不是幂等的成功**：成功后同一活动再打，返回 `code=500 活动时间与已参与活动时间冲突：<活动名>`。
5. **本次实现有缺陷（已记录）**：判定只在 `code=="0"` 时停，而成功码是 1，因此成功后仍继续重试了 40 次（10:00:01 → 10:00:59，间隔 0.8 秒），全部被服务端以冲突拒绝，未产生写入。正确实现应在 `code==1` 时立即停止。

同窗口另一项观测**失败**：静置探测脚本 09:59:40 打开详情页，`page.goto` 45 秒超时（`Timeout 45000ms exceeded`），未产出。「开放那一刻页面自己会不会发 signUp」仍缺。10:01 之后同站点接口恢复正常（一次拉回 316 条），故超时**可能与开放瞬间拥塞有关，但无法断定**。

## 三十七、token 生命上限：测不出来的原因是主动换新（2026-11-03 11:00）

此前一直把「17.5 小时」当经验值，探针报告里又出现三枚都停在 **12.2 小时**的 token，看起来像上限。核对代码后确认：**12.2 小时不是上限，是无人值守重登的换新阈值**。

证据链：

| 环节 | 事实 |
|---|---|
| 探针报告 | 7 枚 token，其中 `T02`、`T03`、`T16` 都是「连续存活 12.2 小时、未观察到失效」，随后被新 token 取代 |
| 换新逻辑 | 自动重登单元每分钟级巡检，`ExecStart=... auto_login.py --preempt`；脚本里 `PREEMPT_HOURS = 12.0`，即年龄到 12 小时就主动换一张新 token |
| 结论 | 探针永远等不到自然过期，因为换新发生在过期之前。能给出的只是**下限 ≥ 12.2 小时** |
| 附带问题 | 同一处的注释写「用到 8 小时时主动换新」，与常量 `12.0` 不一致，属注释过期 |

失效原因的分布（同一份探针日志）：

- **被新会话顶掉**：`T17` 3.5 小时、`T18` 3.0 小时失效，均在另一处登录之后；另有旧 token 在另一环境登录后立即失效的记录。同一账号同时只保留一个有效会话。
- **纯到期**：**没有观测到**。所有失效样本都能对上「换新」或「另一处登录」，没有一枚是放着不动到点自然死亡的。

因此本轮不调整 `PREEMPT_HOURS`：调大它等于让生产环境去赌「token 会不会在学校那边先过期」，代价是推送可能在大半天里全失败；而现有的 12.2 小时下限已经覆盖了两次定时推送之间的间隔。要测真上限，得单独开一条不参与推送的链路，独占账号跑 1–3 天，且期间任何一处登录都会污染实验。

## 三十九、直发路径的两个实现问题（2026-11-03 12:10，如实记录）

直发本身是通的（10:00:01 拿到过 `code=1`，1.14 秒，且不带四个签名头）。但当前实现有两处会让它「看起来在用、实际没用」：

### A. 开关认包名：写死文件名，认不出就静默退回点击

| 位置 | 代码 |
|---|---|
| `local/grab.py:57` | `KNOWN_DIRECT_SCRIPT_BASENAME = "index.b489a1d6.js"` |
| `local/grab.py:2176` | `def _detect_direct_signer()`：只读页面 `<script src>` 的文件名做精确比对，任何异常 `return None` |
| `local/grab.py:2188` | `if base == KNOWN_DIRECT_SCRIPT_BASENAME:` ——认不出就回落到点击路径 |

现场证据：页面现在加载的是 `index.0d1427e5.js`（1,637,068 字节，旧包 1,634,279）。10-31 16:17 的日志还有「入口脚本为已知直发包：启用直发」，11-02 16:57 之后两次提交都只有「第 1 次提交：已发起」，没有「直发已发起」——**退回点击时一行日志都不写**，使用者看不出区别。

后果：平时「能点」时它照样能报上，所以问题被掩盖；一旦是无人值守、页面点不到的场景，就是静默失败。

### B. 版本不兼容的判据是 message 精确相等

`local/grab.py:2297-2303`：只有 `str(code).strip() == "0"` 且 message 去掉句末句号后**精确等于**「版本不兼容，请刷新页面或清除缓存后重试」才 `direct["downgrade"] = True`；文案差一个字，既不判成功也不降级，本场会一直重发到上限。

而响应体里本来就带 `version` 字段（10:00 直发响应里就有），代码没有用它做判断。

### C. 一处需要澄清的（免得把测试脚本的问题算到产品头上）

「10:00 报成后又空打了 40 次」是我临时写的 `direct_new.py` 把判停写成 `code == "0"` 造成的，**不是产品行为**。产品侧在 `local/grab.py:2291` 是以 `code == 1` 判成功，并在 `2620` / `2631` 处以成功为优先退出。

## 四十一、更正：运行时密钥与旧静态密钥是同一个值（2026-11-03 16:45）

第十六、三十九节说「新包里那个旧常量零命中、改用接口下发的运行时密钥」，这句只对了一半。今天在本地做值比对（只打印布尔，不打印值）：

- `POST /upms/security/runtime/profile` 返回体的顶层只有 `code` / `message` / `data` / `version` 四个键，密钥在 **`data`**。
- `data` 是 **16 个 ASCII 字符**（16 字节），混合大小写字母数字，**不是十六进制**；直接按 UTF-8 字节当 AES-128 密钥用，不做二次解码。
- `data` 与代码里那个旧的静态常量**逐字节相同**（比对结果为 true，值本身不在此记录）。
- `local/data/session.json` 只有 `gender` / `name` / `saved_at` / `student_no` / `token` 五个字段，**不含**这个密钥；每次需要时现取。

结论：学校把写死在包里的密钥挪到了接口下发，**值没换**。因此「旧密钥已随旧包失效」这个说法不成立——公开仓库里那个常量至今仍然可用；换登录也不会换它（10-30 起就写死，10-31、11-02、11-03 多次登录后仍是同值）。

这对修订的影响：条款里披露「密钥来自学校接口」没错，但不能据此说「旧密钥已作废」；公开仓库里仍留有可用常量这一点，是要单独处理的风险项。
