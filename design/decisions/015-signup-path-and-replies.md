## 问题

2026-10-31 前后暴露出四个互相牵连的缺口：

1. **直发开关静默失效**：程序按写死的入口脚本文件名判断要不要直发，学校换包后判定失败，
   静默退回点击，不写任何日志——用户以为在用直发，其实没有。
2. **未知回包空打**：回包分类只认少数几句文案；没见过的回包既不判成功也不判失败，
   一直重发到次数上限，给学校和账号都增加压力。
3. **到点不核对**：结果只在预算没用完时才查一次「是否已报名」，到点停下的场次完全没有终态核对，
   用户不知道到底报上没有。
4. **被顶掉就整场作废**：同一账号只保留一个有效登录，server 定时换新会顶掉本机；
   现在的实现遇到登录失效立即终态，计划在等开放时也被整场作废。

## 用户确认的规则

1. **密钥来源**：每场开抢前调一次学校运行时密钥接口；签名用运行时密钥现算，
   密钥只放在本次运行的内存里，不落盘、不写日志；重新登录或回「版本不兼容」时重取一次。
   不再按入口脚本文件名判断直发，也删掉源码里的静态签名密钥。
2. **直发为主、点击兜底**：直发不依赖页面；只有三种情况退回点击——取不到运行时密钥、
   重取密钥后仍「版本不兼容」、同一条没见过的文案连续 3 次。每场都要写日志说明走哪条路、为什么，
   界面计划栏能看到。
3. **回包分类**：按 `code` 加 `message` 里的关键短语判断，不要求整句精确相等；
   日志记完整原文。分类与处理见架构修订设计 3.3 表（成功粘性、名额已满本场直接停、
   冲突先核对 `getJoinInfo`、报名未开始当开门信号、超时重校时、活动不存在直接停、
   登录失效先复查）。
4. **名额已满直接停**：本场结束，结论「名额已满」；不用重试硬扛（热门活动几分钟内就满）。
   以后想继续等，用独立的候补模式（架构修订设计第 6 节，排在「可以以后」）。
5. **终态核对**：每场结束（成功、失败、到点、报名截止后）都调一次 `getJoinInfo`，最多等 3 秒；
   已报名算成功，未报名按实际回包给结论。界面「刷新核对」用同一个接口。
6. **登录失效先复查、再决定**：
   - 只读检查收到一次 4001：隔 1.5 秒复查，连续两次才算失效；
   - 计划在等开放时失效：原地重新登录（能自动登录就自动登录），计划不停；
   - 提交中确认失效：能自动登录就登录一次（限时约 20 秒），成功后重取运行时密钥继续；
     不能自动登录则本场以「登录失效」结束；
   - 报名子进程与界面靠「等待新登录态」交接，登录态只由一个带锁的入口写盘。

## 用户可见行为

- 每场结果都来自学校系统的真实核对（`getJoinInfo`），不再是「本地到点就算结束」；
- 计划栏显示「本场走直发 / 退回点击」及原因；
- 「名额已满」是一种正常结束结论，不算工具故障；
- 等开放时被顶掉，会原地重新登录，计划继续；不能自动登录时才提示用户手动登录；
- 顶栏登录卡不再显示「约剩 N 小时」，改显示上次校验时刻与结果。

## 已知限制

- HTTP 404 / 429 / 5xx 没有真实样本，沿用现有规则，文档标「未验证」；
- 性别不符时学校返回什么码，没有样本，先走「未知文案」规则；
- 报名开放那一秒页面打不开（45–90 秒），页面是否自发 `signUp` 仍未观测——由终态核对兜住；
- 运行时密钥与旧静态密钥是否同源、换一次登录是否变化，尚未确认（只影响公开历史的风险评估）。
