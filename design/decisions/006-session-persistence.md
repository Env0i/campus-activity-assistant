# 006 · 登录态持久化与启动校验

- **状态**：implemented（规则 confirmed 2026-10-24，EXE 迁移 2026-10-25 收口）
- **日期**：2026-10-24 敲定统一数据根与四态校验；2026-10-25 旧 EXE 数据迁移与重建保护验收

## 问题

登录态（cookie/token）是唯一凭证，但存放位置、过期判定和「要不要重新登录」的口径曾經混乱：
重开工具被误要求重登、网络异常被当成失效、重装 EXE 把登录态弄丢——每一次都让用户多输一遍账号密码。

## 用户确认的规则

1. **统一数据根**：开发 / 绿色版在脚本旁 `local/data/`；冻结 EXE（主程序与 grab-worker）默认
   `%LOCALAPPDATA%\TianSoftActivityPreRegistration\data`，环境变量 `CAMPUS_DATA_DIR` 可覆盖；
   主程序与 worker 读写同一份 `session.json` / `storage_state.json`。
2. **启动真实校验、四态结论**：无 session → 「未登录」；有 session 先显示「正在检查登录态」，
   真实访问学校接口后落 **valid / expired / unknown / none** 四态之一——
   不得提前写成「登录有效」，也不得把网络异常说成失效。
3. **只有学校接口明确返回失效（4001 / 明确身份验证失败）才要求重新登录**；
   网络异常显示「暂时无法确认登录态」，保留已有会话，点「刷新」重试，不清登录、不逼重登。
4. 首次使用显示「登录」；**只有真实失效才显示「重新登录」**——两词不混用。
5. 「约 10–17 小时」是实测估算区间，只用于「约剩 N 小时」提醒，**不是保证值，也不作放行 / 拦截依据**；
   登录有效性只由学校接口真实校验决定。
6. **旧数据一次性原子迁移**：冻结版首次使用新数据根时，旧 EXE 旁 `data/` 中缺失的目标文件
   以「临时文件 + `os.replace`」搬入，不覆盖已有新文件；迁移失败不阻断启动。
7. **构建不删登录态**：`build_exe.py` 清理输出目录时保留 `OUT/data`。
8. 会话文件不含账号密码；`start_plan` 是最终防线：非 demo 且最近一次 check 结论不是 `valid` 一律拒绝。
9. （2026-10-25 补充）**应用生命周期元数据只进 `ui.json`**：`last_started_at` /
   `last_heartbeat_at` / `last_closed_at` 由主进程每分钟心跳与正常关闭写入，
   与界面偏好共用同一把持久化锁做原子读-合并-写；`session.json` / `storage_state.json`
   永远只存会话信息。重开时的「上次关闭时长」（正常关闭精确、异常退出只给「约」）与
   「登录预计还剩」都只是提示：估算按 `saved_at` 绝对墙钟跨关闭区间继续计算，
   **不得因旧估算强制过期、清理会话或刷新 `saved_at`**，登录有效性仍只由真实校验决定
   （见 [008](008-lifecycle-version-release.md)）。

## 用户可见行为

- 重开、替换、甚至重建 EXE 都不弹登录窗；界面提示「已复用本机登录态」。
- 断网时胶囊显示「暂时无法确认登录态」，网络恢复点「刷新」即回正常，登录还在。
- 「开始报名计划」在 checking / unknown / none / expired 下都禁用，刷新与登录按钮始终可用。

## 2026-10-26 返修补记（1.1.1 候选）

四态不变；登录剩余一律写「预计/约」，不再出现「一定撑得到」的保证句；粗校时只作提示、不自动校准；演示模式不读凭证。


## 决策 012 修订（2026-10-26 返修轮更新）：登录剩余估算换可信锚点

saved_at 是本机墙钟文本，无法反推真实 UTC：不再拿 datetime.now 减它冒充准确小时数。
锚点只在**登录 worker 的真实成功路径**建立（`_anchor_login_success` 写 `session_timing_v2`：
credential_id/saved_epoch/time_source/uncertainty_s），并要求当时有可信北京时间；
复用与刷新不续期、换凭证换锚点；无锚点/不匹配/时钟不可用 → hours_left=null
（胶囊不报数，时间详情显示「未知（以学校校验为准）」），登录有效性仍只由学校真实校验决定，
估算缺失不要求重登。旧凭证有效性结论不变；未知时间不清凭证、不依赖 OS 估算。


## 2026-11-03 修订（单会话、等开放重登与跨进程交接）

- **同一账号只保留一个有效登录**：新的登录会把旧的顶掉；server 定时主动换新也会顶掉本机
  （实测 11-03 10:35 server 登录，本机 10:44 失效；设计按「会互相顶掉」做，但不依赖它每次准时发生）。
- **等开放时原地重新登录**：计划运行中登录失效，按 [015](015-signup-path-and-replies.md) 先复查，
  确认后原地重新登录（能自动登录就自动登录），计划不停；提交中确认失效则自动登录一次后继续，
  不能自动登录才以「登录失效」结束本场。
- **报名子进程与界面靠 `--relogin-wait` 交接**：worker 确认失效后进入「等待新登录态」，
  界面完成登录并写盘，worker 发现文件更新后重读 token；读盘要能区分「文件不存在」与「读失败」。
- **登录态只由一个带锁的入口写**：界面与 worker 共用同一份 `session.json`，写盘走原子替换与跨进程锁，
  不允许两个进程各自覆盖。
- **代码状态**：待计划 `20261103-arch-b-core` 落地；本记录只先定规则。

## 2026-11-09 修订（登录详情补「预计有效」，10 小时只作提示）

背景：详情卡长期写「学校不公布，工具不估算」，用户无法判断要不要提前重登。
规则 5 仍成立（有效性只看学校校验），本修订只恢复「提示」这一层。

- 估算 = `session_timing_v2` 锚点 + **10 小时**（实测下限）；要求锚点与当前凭证匹配
  且有可信北京时间，否则不报数。估算到点**不**判失效、不清理会话、不阻断报名，
  `session_expired` 始终由学校真实校验决定（`login_rules.build_session_state` 已脱钩）。
- 五种写法：`约到 HH:MM（按登录后 10 小时估，以学校为准）`、跨天
  `约到明天 HH:MM…`、`已过预计时间，学校仍确认有效`、
  `不知道（这次登录不是在本工具里完成的）`、`北京时间校准后再估`。
  真源是 [copywriting.md](../specs/copywriting.md) §3.1。
- 载荷新增 `estimate_reason`（ok / no_anchor / clock_unavailable）；`hours_left`
  重新按锚点给（过点夹到 0），仅作提示展示，不再参与失效判定。
- 放弃的方案：继续不估算（用户无法判断，且已有可靠锚点）；按 17.5 小时实测上限估算
  （单次样本，偏乐观，容易在窗口前误以为还很久）。
- 会再坏的条件：锚点只在新登录成功路径建立，在别处登录/旧登录仍写「不知道」；
  时钟长期不可用时只剩「校准后再估」。
