# 服务器直发签名报名

- **状态**：proposed（2026-11-24 起草；同日用户定下四个问题，见「已定」）
- **来由**：[私聊自助提案](owner-chat-self-service.md) 的 G 项，当时单列不做
- **上游**：[决策 015](../decisions/015-signup-path-and-replies.md)（直发为主、点击兜底，回包分类，终态核对，登录失效先复查）、[决策 002](../decisions/002-signup-modes.md)、[决策 003](../decisions/003-retry-policy.md)、[决策 006](../decisions/006-session-persistence.md)

## 为什么要做

owner 在私聊里点了「预报名」，到点由服务器的 `grab_signup.py` 去报名。它现在只会做一件事：打开详情页，盯着「立即报名」按钮点。本机版在 015 之后已经改成直发签名请求为主、点击兜底，服务器还停在点击上，于是：

- **慢**：开放那一秒页面常常要 45–90 秒才打得开（015 已知限制），点击要等页面，直发不用；
- **不稳**：页面结构一改，点击就失效；直发只依赖接口；
- **两套行为**：同一个人在电脑上和在私聊里预报名，抢法不一样，结果说明也不一样。

## 现状里要先看清的三件事

1. **签名算法**：报名请求的 `hash` 是 `AES-128-ECB(UTF-8("活动id,毫秒时间戳"), PKCS7)` 的小写 hex，密钥是每场开抢前从学校 `runtime/profile` 取的 16 字符运行时密钥（015 规则 1）。本机用 Windows 自带的 CNG（`bcrypt.dll`）算，服务器是 Linux，没有这个接口；Python 标准库也没有 AES。
2. **取密钥是 POST**：要带网关签名头。服务器在私聊自助那一批已经有了标准库实现（`server/scripts/lib/school_detail.py` 的 `sign_headers`），与本机逐字节一致。
3. **主动换新会打断报名**：`auto_login.py --preempt` 在 token 用满 8 小时时主动换新，判断时不看有没有报名正在跑。同一账号只保留一个有效登录（决策 006），换新那一刻旧 token 作废：正在点按钮的页面会被登出；如果 owner 同时开着本机计划，本机也会被顶掉。

## 方案

### S1 签名实现

用 `cryptography` 包的 AES-128-ECB（用户 2026-11-24 定，这是本批唯一的新依赖）：

- 写进 `server/requirements.txt`，部署时在服务器上安装；不进本机安装包，本机照旧用 CNG；
- 只在签名模块里导入；导入失败或调用出错就抛「签名不可用」，本场退回点击，不自造算法（与本机 `SignerUnavailable` 同口径）；
- 签名模块只算签名，不读时钟、不联网、不打印密钥。

对拍样例（假密钥 `Abcdefgh12345678`，由本机 CNG 实现算出，服务器实现必须逐字节相同）：

| 活动 id | 毫秒时间戳 | hash |
|---|---|---|
| `test-activity-1` | `1767225600000` | `e32414cb4f3634022e6adfbb42f1e32ea6b79ae9d39d650ec973ab4ef9753413` |
| 40 个 `a` | `1767225600123` | `f06538985c008b061470062a5ccc92d1f06538985c008b061470062a5ccc92d1fee87e80cd50a7100899d759036b33c9d7cf30c16f023d2df3d50225b40ab818` |

再加一条 FIPS-197 的 AES-128 标准向量，证明调用方式本身没错。

### S2 报名链路：直发为主、点击兜底

照搬本机 015 的规则，不另定一套：

- 开抢前取一次运行时密钥，只放进程内存，不落盘、不写日志；
- 直发走 `GET /rjyHdCyr/signUp/<hash>`，物理并发不超过 2，不自动跟随重定向；节奏沿用服务器现有的黄金风暴、常规全速与 404 自适应退避，次数记账规则不变；
- 退回点击只有三种情况：取不到运行时密钥、重取密钥后仍「版本不兼容」、同一条没见过的文案连续 3 次；
- 回包分类、名额已满直接停、终态以 `getJoinInfo` 核对，都与本机同口径；
- 私聊结果卡写明本场走的是直发还是点击，以及原因。

服务器和本机仍然各有一份实现，不共享运行时代码（AGENTS.md 的既有边界）。回包分类表与节奏常量两边各一份，由对照用例逐条比对，防止两边悄悄分叉。

### S3 登录失效与主动换新

- **等开放期间失效**：先隔 1.5 秒复查一次；确认失效就拉一次无人值守重登（`auto_login.py --force`），重登成功后重取密钥继续；失败就以「登录失效」结束并私聊说明。
- **提交中失效**：与本机一致，限时 60 秒内重登一次（服务器重登要认验证码，比本机慢），成功后重取密钥继续；超时就以「登录失效」结束。
- **主动换新避让**：`--preempt` 遇到下面两种情况就跳过本轮，下一轮再看——有报名单元正在运行；预报名清单里有场次的开放时刻落在接下来 20 分钟内。被动重登（token 已失效）不受影响。
- **直发每次请求现读 token**：换新后下一笔请求就用新 token；运行时密钥与登录无关（015 已知限制），换新后不用重取。

### S4 先拆再加

`grab_signup.py` 819 行、`run_submit_loop` 343 行，都在结构名单里。直接往里加直发会让它们变长，结构检查会红。所以同一份计划分两步：

1. 先只改结构不改行为：拆成签名、直发传输、提交节奏、点击兜底、终态核对几个模块，用离线用例与录制对照证明行为不变；
2. 再加直发、登录恢复和换新避让。

### S5 验证

- **离线**：签名对拍样例；FIPS-197 标准向量；直发与点击的切换条件逐条用例；回包分类与本机对照；换新避让的时间窗边界；`libcrypto` 不可用时退回点击；
- **服务器上的安全演练**：给 `grab_signup.py` 加「直发演练」，只取运行时密钥、算签名、打印走哪条路，**不发 signUp**；先在服务器上跑一次演练，再等一场确实想报的活动做真机验收；
- **真机验收**：一场真实报名，看私聊结果卡里写的路径和原因，以及 `getJoinInfo` 核对结论。

## 不做

- 不做多账号、不代别人报名、不批量占位（硬边界）；
- 不改学校接口契约、不改本机实现；除 `cryptography` 外不加别的依赖；
- 不加候补模式（015 规则 4 的「以后」）；
- 不让服务器感知本机计划：服务器看不到本机有没有在跑，S3 的换新避让只看服务器自己的预报名清单与报名单元。

## 已定（用户 2026-11-24）

1. **签名实现**：引入 `cryptography` 包（没选 ctypes 调系统 OpenSSL，也没选纯 Python AES）。
2. **提交中登录失效**：限时 60 秒重登一次，成功后重取密钥继续，超时以「登录失效」结束。
3. **主动换新避让**：有报名单元正在运行，或预报名清单里有场次在 20 分钟内开放，就跳过这一轮主动换新。
4. **计划安排**：一份计划分两步，先只拆结构、再加直发与登录恢复。

## 风险

- `cryptography` 是带编译产物的包，服务器 Python 版本或架构对不上时装不上；装不上就整场退回点击，部署清单里要先核对安装结果；
- 运行时密钥接口的请求体与成功码仍没有样本（015 已知限制），服务器第一次取密钥可能失败，届时退回点击，演练会先暴露这个问题；
- 服务器重登要认验证码，60 秒内不一定成功；成功率见 `docs/LOGIN.md`；
- 换新避让会让 token 多用一会儿才换：在避让期间 token 刚好自然失效，就会走被动重登。

## 落地后

确认并实现、验收通过后，把 S2、S3 的规则写进决策 015 的修订一节（服务器口径），再把本提案标成 accepted。
