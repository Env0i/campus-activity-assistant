# 代码工程化重构：状态机、单一规则与模块边界

## 状态

proposed（2026-11-12 用户与分支会话、指挥会话讨论定方向；还没审计，没有改代码。1.2.2 发版后才开始）

## 目标

最近几轮反复返工，用户觉得代码质量不行，希望前后端都像成熟工程一样：低耦合、高内聚、分模块，改一处不牵动一片。

已经确认的问题（都有本轮审计或修复的证据）：

1. **界面临时状态有多处可写，退出路径会漏。** 例如「自动登录中」「修改中」卡住，组件「检查中」显示成没装，导入后仍显示失败，以及 `workbench-ui-polish.md` 里的 11 张状态残留卡。
2. **同一条规则写了好几份。** 手机访问的 `phonePhase` 与验证码识别的 `ocrPhase`；下载失败原因表 Python 一份、JS 一份；登录失效的判定桌面一份、手机一份。
3. **大文件挡住并行。** `local/app.py` 约 4900 行（`Api` 约 170 个方法），`local/grab.py` 约 4100 行，`local/ui/m/app.js` 约 3400 行，`local/infrastructure/component_packages.py` 约 1700 行，`local/ui/views/plan-panel.js` 约 1500 行，`local/ui/views/phone.js` 约 1250 行。几乎每份计划都要改 `app.py`，两件事没法同时做。
4. **契约测试按源码字面断言**，只改结构也会变红，让人不敢重构。
5. **前端分层在松动。** 例如 `state/login.js` 调用 views 层的 `reloginAutoLive`。
6. **安装中、更新中这类异步过程没有统一的「进行中」显示**，各处各写一套。

## 非目标

- 不按行数硬拆文件；拆分以职责为准。
- 不换框架、不引入打包器，不重写成另一种语言。
- 不提前抽象：同一件事出现第二次、而且确实要保持一致时才抽。
- 1.2.2 发版前不动结构，只修缺陷。
- 不改学校接口契约、数据模型、登录态机制和报名时序。

## 方案概述

### 1. 原则（学 Java 的原则，不学它的写法）

- **后端（Python）**：按功能拆成 `application/` 服务，依赖由 `app.py` 注入；`Api` 只做转发和参数检查。新代码写 type hints，跨层传递的数据用 dataclass。
- **前端（JS）**：改用 ES Modules（`import`/`export`，用户 2026-11-12 定）；每个功能只有一个状态入口和一组动作；纯函数算出要显示什么，渲染只负责画；按功能分目录。
- **界面状态机**：每个功能一张状态机。所有异步操作统一成「空闲 → 进行中 → 成功 / 失败」。状态以后端为准，前端只补「刚点下去、后端还没回」这一小段。
- **规则只写一份**：两端都要用的，由后端给出结论；实在要两份的，用测试比对，像现在的 `test_reason_maps`。
- **依赖单向**，用测试守住（现有的 `test_layer_boundaries` 扩展到前端）。
- **测试测行为**，不测源码长什么样。

### 2. 先做什么

1. **先改界面状态，不先拆大文件。** 组件、登录、计划栏三块先改成状态机，11 张状态残留卡大多会随之消失。这一步和下一版的界面打磨（`workbench-ui-polish.md`）合成一份计划，免得两边改同一批文件；状态机图并进画板第 8 节。
2. **再拆后端大文件。** 从 `app.py` 的 `Api` 按功能抽服务（更新、组件、手机访问、登录恢复、计划），每抽一块就提交一次。
3. **`grab.py` 最后动。** 它的 stdout 是和界面进程之间的协议，报名链路也在里面。动之前先录一套「同样输入得到同样输出」的对照测试，再小步拆。

### 3. 每一步的规矩

- 只改结构不改行为。全量测试通过、真窗口验过之后单独提交，方便回退。
- 改了分层规则或前端结构，同一提交里修订 `design/decisions/` 里对应的那篇（决策 014 的列表结构和设置抽屉分工，本来就要随界面打磨修订）。

### 4. 审计（重构计划的输入，不另出大报告）

- 只出两份清单：
  - **代码问题清单**：重复的规则、跨层调用、超大函数、隐式状态。
  - **界面状态清单**：每个功能有哪些状态、在哪进在哪出、每个等待操作有没有「进行中」和失败显示。
- 分工（用户 2026-11-12 定）：Fable 5.2 是主模型，出检查清单、下判断并抽查；机械清点和状态路径、依赖追踪交给子模型，子模型可以任意调度（包括其他厂商的 AI），但都要按 Plan Protocol 2.2.1 的计划约束执行。结论写回本提案，或另写一份 proposed 文档，由指挥会话核实后定计划。
- **对抗审计**：用户派出的任何执行模型交回结果后，提交前都要过一轮对抗审计：由另一个模型（或指挥会话）专门找回归、越界改动、漏掉的退出路径和与计划不符的地方，而不是复述执行方的报告。审计意见要带 `文件:行号` 证据；没过就写返修卡，过了才进提交。

- **审计结果**（2026-11-12，执行方 Fable 5.2，基线 `7e2d31c`；指挥会话已抽查核实。补充轮可信度低，已由 Sonnet 盲做重做并经两轮独立对抗审计，见 `redo/`；补充轮的结论以重做为准）：
  - 两份清单：[代码问题清单](../evidence/2026-11-12/refactor-audit/code-issues.md)、[界面状态清单](../evidence/2026-11-12/refactor-audit/ui-states.md)。口径、脚本数出的数字和逐条证据在同一目录的 `README.md`、`inventory.md`、`state-trace.md`。
  - 前端 39 个脚本里有 33 个在同一个依赖环里，`state/` 层有 62 处调用了视图或控制器，三个视图文件直接发桥接请求 24 处；加载期没有环，ES Modules 迁移走得通，但要先把放错层的十来个函数搬走。
  - `Api` 有 153 个方法、23 个在三个以上方法里赋值的标志位、一把被 67 个方法用的锁；测试给 `app` 模块打了 42 个名字的补丁、改写了 `Api` 实例的 66 个成员，拆的时候这些补丁会悄悄落空而不报错。
  - 11 项状态残留里已修 3 项、部分修 1 项、未修 5 项，另有 1 项已知限制和 1 项文案；未修的都是几行的改动，建议在重构前先修。
  - 状态残留的成因有三种：进行中用布尔值、每条出口各自清；一个显示由前端从两个来源拼；程序发起的动作和用户发起的动作靠参数区分。清单里给了每个功能的建议状态机。
  - 手机页没有发现会永久卡住的状态，问题在重复：登录是否失效、立即报名还是预报名、时间是否重叠，手机页各自又推断了一遍。建议不另画状态机，沿用桌面端的，只加手机页的显示。
  - 待用户定：文件与函数大小参考值（清单给了三档，建议新代码函数 60 行、文件 500 行，存量列白名单只许变短）；各功能的状态机（并入画板第 8 节）；重构切法（先修六条缺陷，再铺路、三块状态机、拆 `Api`、`grab.py`）；`local/gui.py` 删不删；安装程序启动后要不要给「重新检查」的出口。

### 5. 保持工程化

- 规范写进 `AGENTS.md`：模块边界、文件与函数大小的参考值（审计后定，超出要在白名单里写理由）、状态机写法。
- 分层测试扩到前端；加文件大小检查和状态机测试。
- 开发期检查工具（用户 2026-11-12 同意引入这类开发依赖，不进安装包）：先上 ruff；mypy 从 `domain/`、`application/` 和新代码开始；前端的 ESLint 等前端结构定下来再加。
- 计划模板加两栏：「所属模块与是否越界」「文档影响」。审计按规范核对；每发一版做一次小审计。

### 6. 文档保鲜

- 每类信息只有一份权威来源，别处只放链接。
- 改代码的同一提交里改文档。能生成的就生成，能用测试比对的就比对。
- 模块说明就近放在模块旁边。提案落地后转成决策，过时内容同时清理。

## 验收标准

- 新增一个状态或一条规则，只改一处。
- 每个临时状态只有一个进口、一个出口；每个等待操作都有「进行中」和失败显示。
- 两个功能可以并行改，不撞文件。
- 只改结构时测试不变红；行为以全量测试加真窗口验收为准。
