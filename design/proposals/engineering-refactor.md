## 目标

最近几轮反复返工，用户觉得代码质量不行，希望前后端都像成熟工程一样：低耦合、高内聚、分模块，改一处不牵动一片。

已经确认的问题（都有本轮审计或修复的证据）：

1. **界面临时状态有多处可写，退出路径会漏。** 例如「自动登录中」「修改中」卡住，组件「检查中」显示成没装，导入后仍显示失败，以及[决策 017](../decisions/017-workbench-refresh.md) 整合的界面打磨前置 11 张状态残留卡。
2. **同一条规则写了好几份。** 手机访问的 `phonePhase` 与验证码识别的 `ocrPhase`；下载失败原因表 Python 一份、JS 一份；登录失效的判定桌面一份、手机一份。
3. **大文件挡住并行。** `local/app.py` 约 4900 行（`Api` 约 170 个方法），`local/grab.py` 约 4100 行，`local/ui/m/app.js` 约 3400 行，`local/infrastructure/component_packages.py` 约 1700 行，`local/ui/views/plan-panel.js` 约 1500 行，`local/ui/views/phone.js` 约 1250 行。几乎每份计划都要改 `app.py`，两件事没法同时做。
4. **契约测试按源码字面断言**，只改结构也会变红，让人不敢重构。
5. **前端分层在松动。** 例如 `state/login.js` 调用 views 层的 `reloginAutoLive`。
6. **安装中、更新中这类异步过程没有统一的「进行中」显示**，各处各写一套。

## 非目标

- 不按行数硬拆文件；拆分以职责为准。
- 不换框架、不引入打包器，不重写成另一种语言。
- 不提前抽象：同一件事出现第二次、而且确实要保持一致时才抽。
- 1.2.2 发版前不动结构，只修缺陷。
- 不改学校接口契约、数据模型、登录态机制和报名时序。

## 方案概述

### 1. 原则（学 Java 的原则，不学它的写法）

- **后端（Python）**：按功能拆成 `application/` 服务，依赖由 `app.py` 注入；`Api` 只做转发和参数检查。新代码写 type hints，跨层传递的数据用 dataclass。
- **前端（JS）**：改用 ES Modules（`import`/`export`，用户 2026-11-12 定）；每个功能只有一个状态入口和一组动作；纯函数算出要显示什么，渲染只负责画；按功能分目录。
- **界面状态机**：每个功能一张状态机。所有异步操作统一成「空闲 → 进行中 → 成功 / 失败」。状态以后端为准，前端只补「刚点下去、后端还没回」这一小段。
- **规则只写一份**：两端都要用的，由后端给出结论；实在要两份的，用测试比对，像现在的 `test_reason_maps`。
- **依赖单向**，用测试守住（现有的 `test_layer_boundaries` 扩展到前端）。
- **测试测行为**，不测源码长什么样。

### 2. 原定实施顺序

1. **先改界面状态，不先拆大文件。** 组件、登录、计划栏三块先改成状态机，11 张状态残留卡大多会随之消失。这一步和下一版的界面打磨（见[决策 017](../decisions/017-workbench-refresh.md)）合成一份计划，免得两边改同一批文件；状态机图并进画板第 8 节。
2. **再拆后端大文件。** 从 `app.py` 的 `Api` 按功能抽服务（更新、组件、手机访问、登录恢复、计划），每抽一块就提交一次。
3. **`grab.py` 最后动。** 它的 stdout 是和界面进程之间的协议，报名链路也在里面。动之前先录一套「同样输入得到同样输出」的对照测试，再小步拆。

### 3. 每一步的规矩

- 只改结构不改行为。全量测试通过、真窗口验过之后单独提交，方便回退。
- 改了分层规则或前端结构，同一提交里修订 `design/decisions/` 里对应的那篇（决策 014 的列表结构和设置抽屉分工，本来就要随界面打磨修订）。

2. **其余前端迁模块**：没排进步骤 1 的 26 个脚本只搬成模块、不改状态，然后上 ESLint。排在三块状态机和界面打磨之后。
3. **后端收尾**：`local/` 下没排进任何一步的 2 个大文件和 6 个大函数，逐个定拆还是留在名单里。排在 `grab.py` 之后。

**并进已有步骤的两件**：mypy 跟着拆 `Api` 走，每抽出一块就把这一块清到 0；组件那块的界面契约测试（15 个测试函数都不跑 node）在组件状态机动手前先补行为测试。

**读证据时要知道的两条局限**：

- 「测试一行都没跑到」的函数清单（`app.py` 46 个、`grab.py` 18 个）只是上限。有的测试不导入 `app.py`，而是把方法抽出来单独求值，覆盖率工具记不到；64 个里有 37 个的名字在测试里出现过。
- 「界面测试字面断言」那张表数的是断言里的字符串，混着断言失败时的提示语和行为测试的期望值，不能当改造预算；预算看同目录的「界面测试函数分类」表。

### 前端目标目录（用户 2026-11-14 定）

桌面端界面改用 ES Modules（见待确认问题 1），目录按功能分：

- 功能目录在 `local/ui/features/` 下，英文短横线小写，定九个——login、components、phone-access、plan、list、clock、terms、update、shell；公共件在 `local/ui/shared/`。
- 文件名决定它属于哪一层——`state.js` 或 `state-` 开头的是状态层，`view.js` 或 `view-` 开头的是视图层，`actions.js` 或 `actions-` 开头的是编排层；`shared/` 下的文件单算公共层。模块入口是 `local/ui/main.js`，挂回 window 的清单是 `local/ui/legacy-globals.js`，兜底与排队是 `local/ui/boot-guard.js`（普通脚本）。
- 模块的层规则——公共层只引公共层；状态层只引公共层和状态层；视图层可引公共层、状态层、视图层；编排层和 `main.js`、`legacy-globals.js` 不限。跨功能引用允许，但受同一条层规则约束。还没迁的普通脚本仍按目录认层，现有白名单的含义不变。

迁移方向是「自上而下」：因为普通脚本先跑，模块可以直接用普通脚本的全局名字，普通脚本要用模块里的函数就经 window 上挂的名字。所以状态仓库 S、时间工具、桥接这些被所有文件用的公共件最后迁，不是最先迁。

## 验收标准

- 新增一个状态或一条规则，只改一处。
- 每个临时状态只有一个进口、一个出口；每个等待操作都有「进行中」和失败显示。
- 两个功能可以并行改，不撞文件。
- 只改结构时测试不变红；行为以全量测试加真窗口验收为准。

## 后续实施计划

建议按业务验收逐步交付。每批先定一个能独立说明的操作，写清入口、数据从哪来、谁更新状态、结果如何回到界面。抽出服务后，从 `Api` 顺着一次调用就能找到实现。独立合入前，按原提案做全量回归和本批涉及的窗口验收。

### A. 收口本机版 Api

沿用续跑计划 `20261118-api-refactor-repair` 的分段。按 2026-11-18 确认的口径，**1,200 行是参考目标**。按职责归属、接口行为和离线回归验收，收尾记录 `app.py` 实际行数和留在原文件的装配职责。执行中的续跑按此口径衔接。

| 分段 | 交付结果 | 验收场景 |
|---|---|---|
| 登录恢复和活动列表 | 登录恢复服务持有最近一次检查结论，列表服务持有请求、缓存和错误状态。其他调用方读取副本，`Api` 接口沿用原签名。 | 重复检查仍会补查，失效时仍走原来的恢复分流。列表成功时提交缓存，失败时保留原有错误状态和界面契约。复用 `test_login_*.py`、`test_list_signed.py` 和现有并发用例。 |
| 计划接纳、发布和取消报名 | 报名计划服务接管开始请求、去重、取消、终态和计划快照。接纳与占位受同一把协调锁保护，事件发布在锁外。 | 两个请求竞争时只接纳一个，已取消的请求不会启动，迟到事件归属原计划，终态只发布一次。复用 `test_signup_plan.py`、`test_cancel_signup.py` 和现有并发用例。 |
| 桌面外壳与启动 | 把窗口、托盘、时钟、进程监督、启动和退出等辅助逻辑归到对应职责。 `app.py` 保留窗口启动、依赖组装和兼容接口。 | 演示模式、命令行入口、资源定位、关停顺序和进程树回收保持原行为。复用 `test_ui_main_window.py`、`test_business_clock.py` 和 worker 测试。 |

### B. 按功能整理桌面前端和手机页

1. **桌面剩余脚本**逐块迁入已有的 `features/`。确认剩余普通脚本已无引用后，再移除对应的兼容全局名，公共状态、时间工具和桥接按第 7 节的约定最后迁。桌面状态机与原型验收按功能核对，界面调整单独列出用户可见差异。沿用现有 Node 行为与界面契约测试。
2. **手机页**已按普通脚本拆分，原因见 keepalive-probe 证据；规则改用后端字段按组另开批次。后续先整理请求、配对和会话恢复，再迁状态更新与渲染，最后迁报名计划操作。登录结论、报名模式和冲突判断使用后端已有字段。每批验证配对、重连、状态刷新和动作确认中的对应路径，使用 `test_phone_ui.py`、`test_phone_service.py` 和 `test_phone_infra.py`。静态脚本沿用 `PHONE_STATIC` 的显式登记，并保留原提案的真机和打包加载验收。

### D. 收尾长文件与开发检查

- `component_packages.py` 按包校验、缓存与安装事务的维护任务拆。重点核对旧版本保留、切换和失败回滚，复用 `test_component_packages.py`。

- 桌面样式随界面打磨按功能整理。大型测试文件随对应功能核对重复覆盖，复用原有测试文件与业务类。
