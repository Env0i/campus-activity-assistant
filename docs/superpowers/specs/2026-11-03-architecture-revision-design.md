## 3. 报名链路

### 3.1 直发：密钥改从学校接口取，不再认文件名

**事实。**
- 签名算法是 `AES-128-ECB + PKCS7`，明文 `"{活动ID},{毫秒时间戳}"`，输出 96 位小写 hex。时间戳有效期约 60 秒（签名材料 §5）。
- 页面点击前会调 `POST /upms/security/runtime/profile`，返回一个 16 位的运行时密钥（实测 §28、§34）。用它现算的 hash，两次真实报名都拿到了 `code=1`。
- 现在的开关 `_detect_direct_signer`（`local/grab.py` 约 2176 行）只比对 `KNOWN_DIRECT_SCRIPT_BASENAME`（57 行）。学校换文件名后，它返回 `None`，静默走点击。

**新做法。**
1. 每场开抢前（登录检查通过后）调一次 `runtime/profile`，取运行时密钥。密钥只放在这次运行的内存里，不落盘、不写日志。
2. 开抢时用运行时密钥现算 hash，发 `GET /rjyHdCyr/signUp/<hash>`。请求头只带 `Accept`、`token`、`Referer`、`User-Agent`，和现在一样。
3. 重新登录后、或回包「版本不兼容」时，重新取一次密钥。
4. 删掉 `KNOWN_DIRECT_SCRIPT_BASENAME`、`_detect_direct_signer` 的文件名比对，以及 `local/signup_signing.py` 里的静态密钥 `_SIGN_KEY`。`build_signup_hash` 改成接收密钥参数。
5. **直发不再依赖页面。** 浏览器只在需要点击兜底时才用。
6. 走直发还是点击，每场都写一行日志，说明用的哪条路、为什么；计划栏也要能看到。

**什么时候退回点击**：取不到运行时密钥；重取密钥后仍回「版本不兼容」；同一条没见过的文案连续 3 次（见 3.3）。

**开抢前预检（建议改，见第 11 节 S1）**：开放前 30–60 秒发一次 signUp。回「报名未开始」说明密钥和格式都对；回别的，就提前打开页面准备点击。这一次请求会被学校拒掉，不会写入。

### 3.2 点击：降为兜底

- 开放那一刻页面可能进不去，所以点击兜底要**提前约 3 分钟打开详情页**，不能等开抢时再开。
- 页面流程是：客户端先自查（时间冲突、已报名直接拦下，不发请求）→「立即报名」→ 二次确认「是否确认报名此活动？」→ 发 1 条 signUp（实测 §34、§35）。
- `uni-button` 要用真实指针事件点，DOM 的 `click()` 不触发业务（实测 §34）。产品现在的点击实现在 10-27 有过真实成功，实现时复核一遍。

### 3.3 回包分类表

学校把业务结果放在 HTTP 200 的 `code` 和 `message` 里。按 `code` 加 `message` 里的关键短语判断，不要求整句精确相等；日志记完整原文，不再截到 30 个字（现在 `_apply_conclusion` 用的是 `message[:30]`）。

| 回包 | 含义 | 处理 |
|---|---|---|
| `code=1`「操作成功！」 | 报上了 | 成功，粘性，停 |
| `code=500`「报名未开始！」 | 发早了，学校严格卡秒 | 继续，按开抢节奏发 |
| `code=500`「报名人数已满」 | 满了 | **本场结束，结论「名额已满」**；以后可以转候补（第 6 节） |
| `code=500`「活动时间与已参与活动时间冲突」 | 冲突，或自己刚报上 | 停。先用 `getJoinInfo` 核对：已报名算成功，否则结论「时间冲突」 |
| `code=500`「报名已结束！」 | 窗口关了 | 停，结论「报名已截止」 |
| `code=0`「版本不兼容」 | 密钥或明文格式不对 | 重取一次密钥再算；仍然这样就退回点击 |
| `code=0`「您的请求已超时」 | hash 里的时间戳超出约 60 秒 | 重新校时再算；连续 2 次就停，提示本机时钟有问题 |
| `code=0`「Cache 'hd-info' does not allow null」 | 学校查不到这个活动 ID | 停，结论「活动不存在」 |
| `4001` 或「身份验证失败」 | 登录失效 | 见 4.2、4.3 |
| HTTP 404 / 429 / 5xx | 没有真实样本 | 沿用现有规则，文档标「未验证」 |
| 其他 | 没见过 | 同一文案连续 3 次就退回点击；退回后仍一样就停 |

补充：
- 回包里还有一个 `version` 键，含义不明。只记日志，不参与判断。
- 性别不符时回什么，还没有样本。在那之前走「其他」这一行。
- 名额已满原来按决策 003 第 6 条可以重试，现在改为终态。理由：热门活动几分钟内就满，学校页面自己也不重试，一直打只会给学校加压力。

### 3.4 开抢时机与时钟

- 学校提前 1 秒就回「报名未开始」（实测 §28）。
- 本机时钟比学校慢约 0.53 秒，而且偏得很稳定；用 HTTP `Date` 校时，精度只有 ±1 秒（实测 §20）。
- 建议：把「报名未开始」当作还没开门的信号，开抢前收到的不计入最大提交次数；超过预期开放 3 秒后仍是「未开始」，就按慢节奏发。

### 3.5 终态核对：总用 `getJoinInfo` 查一次

- 接口：`POST /rjyHdCyr/getJoinInfo/<活动ID>`。未报名返回 `code=1, data=null`；已报名时 `data` 带 `sfbm=1` 和报名时间 `bmsj`（实测 §34）。
- 现在 `_finalize_once` 只在预算没用完时才查（`can_check = bool(state["attempts"]) and not budget.expired()`，约 2743 行）。改成每场结束都查一次，最多等 3 秒，报名截止之后也查。
- UI 的「刷新核对」用同一个接口，列表的 `signed` 作辅助。

### 3.6 RISK-001 关闭

- 直发模式下，页面上的请求本来就不记账：`on_request` 一开始就返回。
- 点击模式下，点一次就是 1 条请求。
- 还没观测到的只剩「开放那一秒」，因为那一秒页面打不开。这个缺口由 3.5 的终态核对兜住。

## 4. 登录态

### 4.1 事实

- 同一账号基本只保留一个有效登录，新的登录会把旧的顶掉（实测 §37）。
  - 例：11-03 10:35 server 自动登录，本机 10:44 就失效了。
  - 也有对不上的：11-02 16:45 本机登录后，server 到 19:20 才失效。所以设计按「会互相顶掉」来做，但不依赖它每次都准时发生。
- server 最近 7 天自动登录 19 次，一部分是定时主动换新，一部分是收到 4001 后重登（回填 4.5）。
- 没观测到 token 自然过期，存活下限是 12.2 小时。所谓 17.5 小时是写死的常量（实测 §4、§37）。
- 13 枚失效过的 token 里，只有 1 枚失效后又恢复（服务器检查第四节）。

### 4.2 失效判定：先复查一次

- **只读检查**（启动校验、开抢前检查、`probe_token`）收到一次 4001：隔 1.5 秒复查，连续两次才算失效。现在 `probe_token`（约 1790 行）一次就判失效。
- **提交中**收到 4001：先停发，只读复查一次，确认后再按 4.3 处理。

### 4.3 失效之后

- **计划在等开放时**：原地重新登录，计划不停。
  - 能自动登录的（有账号密码、也有验证码识别），就自动登录。
  - 不能的，在计划栏提示重新登录，规则按 UI 设计 9.3。
  - 现在 `_auto_relogin_eligible`（`local/app.py` 约 1364 行）在计划运行时排除自动登录，要放开。
- **提交中确认失效**：
  - 能自动登录，就自动登录一次，限时约 20 秒。成功后重新取运行时密钥，继续到窗口关闭或预算用完。
  - 不能自动登录，本场以「登录失效」结束。
- **实现要点**：worker 和界面是两个进程，共用 `local/data/` 下的登录态文件。worker 确认失效后进入「等待新登录态」，由界面完成登录、写盘；worker 发现文件更新后重读 token。写盘已经是原子替换，读盘要能区分「文件不存在」和「读失败」（实测 §21）。
- 决策 003 第 6 条（登录失效立即终态）要相应修改。

### 4.4 server 主动换新

- 仓库 `server/deploy/auto_login.py` 里 `PREEMPT_HOURS = 8.0`，线上是 12.0，两边不一致（实测 §37）。
- server 每次登录都会顶掉本机。本机按 4.3 处理以后，这件事就不致命了。server 侧只做小同步：统一成一个值，并考虑只在推送前换新。放在「可以以后」那一档。

### 4.5 不再显示「剩余时间」

真实界面上，刚登录也只显示「剩余时间未知」（实测 §4）。改成显示「上次校验时刻和结果」，并删掉这三处常量：`local/app.py:102` 和 `local/gui.py:40` 的 `TOKEN_LIFETIME_H`，以及 `local/grab.py:906` 的「有效期约 17 小时」。

## 5. 活动状态

- 状态只看报名窗口，规则沿用 `signup_plan.classify_signup_mode` 和决策 002 第 2 条。
- 「活动已开始但报名还开着」在 316 场里 0 例。报名截止和活动开始之间的间隔都是半小时的整数倍，像是后台规则算出来的（推断）。另有 18 场两者同秒，按 `now < sign_end` 判断已经正确。
- 不加专门字段、提示样式或「只走点击」的分支。
- server 的 `item_status` 把已开始的活动当成已关闭，实际效果和上面等价，不改。

## 6. 候补模式（排在最后）

**用户 2026-11-03 定：写进方案，排在「可以以后」。** 要等 3.1、3.3、4.3 做完再做。

- **不能只读判断有没有空位。** 学校没有「已报名人数」字段，页面也不显示已满，只有上限 `bmrssx`。所以**每检查一次，就是一次真实的报名提交**，空出来就直接报上。
- **由用户逐场点「转为候补」**，不自动接在开抢后面。
- 只走直发；直发不可用时不启动。
- 每 2 分钟发 1 次（约每场每小时 30 次），最多同时候补 3 场。
- **什么时候停**：报名截止、报上、回「时间冲突」、回「报名已结束」、确认登录失效。
- 报上要醒目通知（界面；配了飞书的话也推飞书），提醒按时签到、不去要及时退。
- 必须配自动登录：server 定时换新会在候补期间顶掉本机。
- 日志单独记一类，比如 `kind=waitlist`。
- **风险**：长时间、规律的请求比开抢那一下更像脚本，学校既没禁止也没授权；空出来的名额补得很快（实测 §36、§40），抢到的概率不高。条款要披露。

## 8. 条款 r4

- `TERMS_VERSION` 从 `2026-10-27-r3`（`local/app.py:198`）升到 r4，要求重新同意。只有 1 人在用，成本很低。
- **披露**（正文措辞由用户过一遍）：
  1. 报名默认用直发：不经过学校页面，直接调用报名接口；会向学校取运行时密钥，只放在本次运行的内存里。
  2. 活动列表、详情、报名核对都直接调用学校接口。
  3. 自动登录会替你勾选学校登录页的《隐私协议》；用接口登录时，完全不经过学校登录页。
  4. 开抢时短时间内会多次提交；候补模式会长时间低频提交。
  5. 用本工具登录，会让同一账号在其他地方的登录失效（包括手机上的学校页面和 server）。
  6. 学校规则：只找到登录页的《隐私协议》，其中没有关于脚本或自动化的条款；没有找到其他校规。工具不声称合规。按协议 2.2，账号名义提交的一切由账号本人负责。
  7. 只服务本人账号。
- `docs/USER_AGREEMENT.md` §3 在直发模式下已经不准确，r4 一并改掉。

- **构建时注入**：站点地址等常量在构建时注入（已定）。

## 13. 给 UI 设计第 13 节的答复

1. **计划等开放时能不能原地重新登录**：能，计划不停。开抢前 100 秒内和提交中，只做自动登录；不能自动登录的，本场以「登录失效」结束，计划栏写明后果（4.3）。
2. **条款正文和版本号**：升到 r4，披露清单见第 8 节，正文由用户过一遍。
3. **「刷新核对」用什么**：`getJoinInfo`，列表的 `signed` 作辅助（3.5）。
4. **活动已开始的场次**：不加提示样式，也不走单独路径，状态只看报名窗口（第 5 节）。

另外几条要 UI 跟着改：
- 计划栏要能显示「本场退回点击」和原因。
- 「名额已满」是一种结束结论，不算工具失败。
- 顶栏登录卡不再显示剩余时间。
- 候补入口排在最后，等第 6 节开工再画。

## 14. 放弃了什么

| 放弃的做法 | 为什么 |
|---|---|
| 按入口脚本文件名判断要不要直发 | 学校一发版就静默失效，已经发生过 |
| 下载学校脚本，按内容识别签名 | 体积大、会误判；学校已经有现成的取密钥接口 |
| 只看回包里的 `version` 字段 | 含义不明 |
| 给直发补上四个签名头 | 实测不需要；补了反而多一个会跟着学校变的依赖 |
| 「活动已开始」的专门分支和提示样式 | 316 场里 0 例，写了也永远进不去 |
| 名额已满时低频重试 | 用户定为直接停；想继续等，用单独的候补模式 |
| 调 404/429 规则 | 没有样本，调了也没法验证 |
| server 同步本机的退避和签名规则 | 预报名没人在用 |
| 测 token 的真实寿命 | 要独占账号跑 1–3 天，其间任何一次登录都会污染结果 |
| 继续守「开放那一秒」的页面观测 | 那一秒页面打不开；直发不依赖页面以后，这一项不再影响设计 |

## 15. 什么条件下会再坏

- 学校改了 `runtime/profile` 的路径或返回格式：取不到密钥，退回点击（可见）。
- 学校改了明文格式或加密算法：回「版本不兼容」，退回点击。
- 学校改了回包文案：先走未知文案规则，3 次后退回点击，分类表要更新。
- 学校开始校验签名头：直发全部被拒，退回点击；那时再按 L4 的核实结果决定补不补。
- 学校开始返回真实的 404/429：现有退避没验证过，要看日志再调。
- 学校改了单会话规则，或 server 换新更频繁：本机提交中失效会更多，要看自动登录的成功率。
- 校时只到秒：学校在秒边界上更严，或本机时钟偏得更多，开抢的前一两秒会落空。
- 学校出现「报名截止晚于活动开始」的活动：状态规则不用改，但时间冲突检查要复核。
